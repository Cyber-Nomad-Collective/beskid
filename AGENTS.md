## Learned Workspace Facts
- This workspace is an aggregate superrepo where core code lives in submodules, especially `compiler`, `pckg`, and `beskid_vscode` (VS Code extension sources for aggregate/Open VS X workflows).
- Corelib (standard library) is expected via the nested `compiler/corelib` submodule (`beskid_standard` repo, not a top-level superrepo submodule); the canonical Beskid package sources live at `beskid_corelib/` with **pckg package identity `corelib`** (legacy `standard_library` paths may still be accepted by tooling). The separated workspace layout uses the repo root as `BESKID_CORELIB_ROOT` (must contain `beskid_corelib/Project.proj`); corelib CI publish/pack must not assume `.ci-cache/beskid_corelib`. Arrays are intended as a primitive Beskid type with unified compile-time length semantics where the type system allows. Syscall-backed runtime I/O lives under `packages/runtime/src/System` as split `Input` / `Output` / `Error` surfaces; higher console/ANSI work belongs in a dedicated `corelib_console` (or equivalent) package, not monolithic `IO.bd`. Beskid CLI packing can place generated Markdown and structured `api.json` under `.beskid/docs/`; registry listing, serving, and `beskid_pckg` ingestion should treat those paths as first-class. Structured **`api.json` is the primary contract** for pckg docs: hierarchical members/types, compiler-derived signatures and `typeRef` links for all resolved symbols (documented or not, with null doc fields when prose is absent)—not parallel string-key grouping outside the JSON schema.
- The `pckg` service is deployed in containers with compose-managed database connectivity, HTTP port binding, artifact storage paths, and optional captcha keys; when no users exist yet, the first administrator is created through the interactive in-app onboarding flow. EF Core migrations apply at application startup by default (`Pckg:Database:AutoMigrateOnStartup`); routine deploys should rely on that path (including legacy schema repair when history drifts) unless operators explicitly disable auto-migration.
- Prebuilt Beskid CLI binaries are published from the `compiler` repo CI to **GitHub Releases** on the rolling tag `cli-latest` (install scripts under `site/website/public/` point at those URLs; user-facing download docs may also reference `cdn.beskid-lang.org` under the `beskid-lang.org` domain).
- Open VS X publishing for the VS Code extension uses a matrix that includes `darwin-arm64` and `darwin-x64`; the `darwin-x64` job sets `OPENVSX_RUST_TARGET` to `x86_64-apple-darwin` so the bundled Intel LSP matches the `darwin-x64` VSIX when CI runs on Apple Silicon hosts (`noxfile.py` / `ci/open_vsx.py` / `.github/workflows/publish-open-vsx.yml`). `vsce package` rejects `@types/vscode` versions above the declared `engines.vscode` range, so typings must stay aligned with the extension engine pin.
- Compiler CI can publish the **`corelib`** package to **pckg** using the `BESKID_PCKG_KEY` GitHub Actions secret (alongside CLI release automation).
- The repo uses `.cursorignore` with a negated `!references/` pattern so gitignored reference trees stay available for Cursor indexing and `@` mentions; opinionated formatter work is often compared to the in-repo **bsharp** reference under `references/bsharp` (C#-style `Emit` patterns).
- `pckg` **Server.Tests** disables xUnit assembly and collection parallelization via `xunit.runner.json` copied into the test output to reduce intermittent failures when the hosted test server starts under full-suite load.
- Package upsert and summaries support an optional **iconUrl** (HTTP/HTTPS only, length-capped to match storage); dashboard metadata flows and package detail pages surface it with image fallback when loading fails.
- Canonical cross-cutting specification content for the project is maintained under `site/website/src/content/docs/platform-spec/`; Astro 6.x site builds expect Node ≥22.12 for `astro build` in CI and production (avoid relying on a Bun-reported Node 20 stub for Astro). Website container builds use a root `.dockerignore` to keep Docker/Podman build contexts small; `site/website` image builds may set `BESKID_SKIP_TRUDOC_VERIFY=1` when full trudoc prebuild verify cannot run under Bun in Linux containers while CI still enforces contracts separately. In platform-spec MDX, escape angle-bracket generics in tables and prose (for example `` `Spanned<Program>` ``) so MDX does not treat them as JSX components. Platform-spec reader shell rules are mirrored in `packages/beskid-docs-ui/src/styles/platform-spec-core.css` and `packages/trudoc/css/platform-spec-core.css`; update both together when changing typography, layout, or base `font-family`, and regression-test platform-spec top navigation plus tab panels so visible content tracks the active tab after shell CSS edits.
- Platform-spec documentation structure and metadata are validated with trudoc/Zod under `packages/trudoc/src/platform-spec/`; CI is expected to surface clear errors when frontmatter, graph links, or per-node templates drift from the schemas.
- Compiler mods use a dedicated project type (`Mod`/`CompilerMod`) discovered through compiler-sdk contracts (`Generator`, `Analyzer`, `Rewritter`) with AOT-only execution; language-level `meta` block grammar is removed, and Rust-only compiler composition (host/composition syntax, pipeline phases) stays separate from Beskid-side mod SDK behavior. The compiler itself is never written in Beskid. Beskid optional types are `Option<T>` only (not an `optional` keyword). Rust AST is canonical: `Beskid.Compiler.*` SDK sources (including `Query.bd`) are generated via `beskid_ast_reflect_gen`, not hand-maintained parallel syntax. IoC/DI is compile-time inside the Rust host and read-only to mods/SDK. The corelib repo is split into interlinked workspace packages.
