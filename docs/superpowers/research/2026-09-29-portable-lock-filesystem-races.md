# Staged registry publication and path races (Rust 1.98.1)

## Decision for v0.5

Treat the registry root and its staging area as trusted, permission-protected storage. Under that contract, build a complete private staging directory on the same filesystem, validate it, and publish it once; readers should validate the published manifest and content. A cooperative lock can serialize beskid writers, but cannot exclude another local process with write access to the root. Do **not** describe a path-based `std::fs` implementation as safe against that concurrent actor. If that actor is in scope, require a platform-specific handle-relative implementation and tests on the actual supported filesystems before claiming the stronger property.

## Publication primitive

| Platform | No-replace publication of a staged directory | Qualification |
| --- | --- | --- |
| Linux | `renameat2` with `RENAME_NOREPLACE`, relative to pinned parent directory descriptors. | Fails with `EEXIST` when destination exists; filesystem support varies. `renameat2` is Linux-specific. [Linux rename(2)](https://man7.org/linux/man-pages/man2/rename.2.html) |
| macOS | `renameatx_np` with `RENAME_EXCL`, relative to pinned parent descriptors; `RENAME_NOFOLLOW_ANY` and `RENAME_RESOLVE_BENEATH` are available flags. | `RENAME_EXCL` is conditional on volume support (`VOL_CAP_INT_RENAME_EXCL`), per the installed macOS `rename(2)` manual. Apple's exported [header declares the API and flags](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/sys/stdio.h#L371-L400). Unsupported volumes must fail closed. |
| Windows | Open the staged directory as a handle and call `SetFileInformationByHandle(FileRenameInfo)` with `FILE_RENAME_INFO.ReplaceIfExists = FALSE`; `RootDirectory` can pin the destination parent. | Microsoft's contract says an existing destination returns an error. Sharing rules, filesystem drivers, and rename support can still make a move fail. [FILE_RENAME_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_rename_info), [SetFileInformationByHandle](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-setfileinformationbyhandle) |

Stable `std::fs::rename` has **replace** semantics and different destination behavior across Unix and Windows; it is not a portable no-replace primitive. A preceding `exists`/`symlink_metadata` check is a race. `OpenOptions::create_new` is atomic for a **file**, including when a dangling symlink occupies its final name, but does not publish a populated directory. [Rust `rename`](https://doc.rust-lang.org/std/fs/fn.rename.html), [Rust `OpenOptions::create_new`](https://doc.rust-lang.org/std/fs/struct.OpenOptions.html#method.create_new), [Rust TOCTOU guidance](https://doc.rust-lang.org/std/fs/#time-of-check-to-time-of-use-toctou).

## Reading below a root

For a hostile concurrent writer, hold an already-validated directory handle and resolve each child relative to it without following links. On Linux, `openat2` can combine `RESOLVE_BENEATH` or `RESOLVE_IN_ROOT` with `RESOLVE_NO_SYMLINKS` (and `RESOLVE_NO_XDEV` if crossing mounts is forbidden); `O_NOFOLLOW` alone applies only to the final component. A component-by-component `openat` traversal with directory descriptors and no-follow flags is the older Unix pattern. [Linux `openat2(2)`](https://man7.org/linux/man-pages/man2/openat2.2.html), [Linux `openat(2)`](https://man7.org/linux/man-pages/man2/openat.2.html). On macOS, use descriptor-relative `openat` for each component with `O_DIRECTORY|O_NOFOLLOW`, then inspect/open through held descriptors; the installed macOS `rename(2)` manual also documents the rename no-follow flag and Apple's [exported header](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/sys/stdio.h#L371-L400) names it. On Windows, native `NtCreateFile` supports a `RootDirectory` handle and `FILE_OPEN_REPARSE_POINT`; `OBJECT_ATTRIBUTES.OBJ_DONT_REPARSE` rejects reparses encountered while parsing a name. Ordinary `CreateFileW(FILE_FLAG_OPEN_REPARSE_POINT)` only documents opening the link itself at the final name and does not supply a parent-handle-relative traversal API. [Microsoft `NtCreateFile`](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-ntcreatefile), [`OBJECT_ATTRIBUTES`](https://learn.microsoft.com/en-us/windows/win32/api/ntdef/ns-ntdef-_object_attributes), [`CreateFileW`](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew), [reparse points](https://learn.microsoft.com/en-us/windows/win32/fileio/reparse-points).

Rust 1.98.1's `std::fs::symlink_metadata` observes one path at one instant and cannot bind later reads to the same object. The emerging `std::fs::Dir` handle-relative API is **nightly-only** and offers only `open_file`/`metadata` today, so stable `std` cannot provide the full traversal-and-rename protocol. [Rust `symlink_metadata`](https://doc.rust-lang.org/std/fs/fn.symlink_metadata.html), [Rust `Dir`](https://doc.rust-lang.org/std/fs/struct.Dir.html).

## Guarantee boundary and cost

A successful same-filesystem rename can make a finished directory appear under its published name in one namespace operation; it does **not** freeze its contents, authenticate bytes, provide crash durability by itself, or prevent a writer with parent permissions from subsequently replacing/removing the name. Holding handles prevents path substitutions from redirecting an operation, but an adversary who can mutate files within the held directory or change the root's ACLs remains outside this guarantee. Network and unusual filesystems need explicit qualification: Linux even notes that an NFS rename error may follow a completed server-side rename. [Linux `rename(2)`](https://man7.org/linux/man-pages/man2/rename.2.html), [Rust TOCTOU guidance](https://doc.rust-lang.org/std/fs/#time-of-check-to-time-of-use-toctou).

The v0.5 low-cost route is therefore a documented trusted-root/ACL assumption, same-filesystem staging, fail-closed validation, and atomic publication only where the OS no-replace primitive is supported. Supporting an untrusted local concurrent actor on all three targets is a distinct, higher-cost security feature: native wrappers, ownership and reparse-point rules, volume capability handling, and adversarial race tests on Linux, macOS, and Windows. `std::fs` alone cannot substantiate that claim.
