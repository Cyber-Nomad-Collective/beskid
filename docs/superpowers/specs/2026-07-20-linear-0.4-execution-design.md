# Beskid 0.4 Linear Execution Design

## Goal

Make Linear an executable delivery projection of the repo-authoritative OpenSpec change `hir-free-isle-abi-v5-native-runtime`, with explicit ownership, dependency order, repository scope, and acceptance evidence for every 0.4 work item.

## Sources of truth

1. Normative behavior: `openspec/specs` plus the active OpenSpec deltas under `openspec/changes/hir-free-isle-abi-v5-native-runtime/specs`.
2. Migration completion ledger: `openspec/changes/hir-free-isle-abi-v5-native-runtime/tasks.md`.
3. Execution ordering and evidence boundary: `docs/superpowers/plans/2026-07-14-0.4-release-closure.md` and `docs/superpowers/reports/2026-07-20-0.4-readiness-baseline.md`.
4. Delivery projection: Linear project `Beskid 0.4 Release`.

Linear records ownership and delivery state; it does not supersede OpenSpec requirements or repository evidence.

## Considered structures

### Preserve W1–W7 and enrich every issue — selected

Keep CYB-5 through CYB-44 as the original wave and implementation hierarchy. Add W0 for completed foundation evidence, fill uncovered implementation ownership with CYB-64–67, add a uniform execution contract to every issue, correct dependency links, label ownership, and add only bounded Cursor support leaves CYB-68–71. This preserves existing history and gives each agent an isolated, reviewable unit.

### Create one issue per OpenSpec checkbox — rejected

This offers literal checkbox parity but duplicates the existing 40-issue hierarchy, fragments acceptance evidence, and makes completion drift likely because sections 1–6.10 intentionally restate the same migration at different levels.

### Keep detail only in one Linear document — rejected

A single document is compact but cannot express per-item ownership, blocking relations, estimates, status, or evidence. Agents would still need to reinterpret the document before each run.

## Linear hierarchy

- W0 / CYB-63 and CYB-72–74: completed contract foundations and historical baseline evidence.
- W1 / CYB-5: production `TypedProgram` → `CodegenInput` → ISLE → verified CLIF authority.
- W2 / CYB-6 and CYB-64: generation-safe semantic facts and diagnostics.
- W3 / CYB-7: exact ABI-v5 runtime-kit discovery, validation, AOT, and JIT/REPL consumption.
- W4 / CYB-8 and CYB-65: remaining codegen, frontend, document, and LSP consumer migration.
- W5 / CYB-9 and CYB-66: canonical runtime corpus, consumer/bundle cutover, and Linux/macOS/Windows kit matrix.
- W6 / CYB-10 and CYB-67: HIR, `Lowerable`, Rust runtime, ABI dispatch, fallback, dependency, and generated-artifact retirement.
- W7 / CYB-11 with Cursor support CYB-68–71: fresh release verification, documentation, review, and sign-off.

CYB-12 through CYB-44 remain the original implementation leaves. CYB-64–67 close OpenSpec coverage that previously existed only in broad parents; CYB-68–71 are isolated support leaves. A leaf is complete only when its exact acceptance commands are freshly run and the result is attached or commented in Linear.

## Ownership policy

`agent/codex` means Codex owns implementation, review, integration, and completion decisions. All compiler/runtime behavior, semantic authority, migration, deletion, cross-target integration, and final sign-off work uses this label.

`agent/cursor` means Cursor owns a bounded support task that cannot independently change the release architecture. Cursor scope is limited to documentation/OpenSpec bookkeeping, CI/configuration checks, test-fixture or command-log collection, package-content inventories, and mechanical audit preparation. Cursor work hands evidence to a Codex-owned parent; it cannot close that parent or mark the release ready.

No active issue carries both agent labels. Completed historical Cursor alignment items retain `agent/cursor` for provenance.

## Issue execution contract

Every active release issue contains:

1. Outcome and ownership boundary.
2. Exact OpenSpec task and requirement mapping.
3. Repository paths in scope.
4. Explicit prerequisite and blocking links.
5. Numbered implementation steps, including a failing test or audit before behavioral changes.
6. Exact focused verification commands and expected evidence.
7. Handoff rule stating what the next issue may consume.

Parent waves describe integration order and exit criteria. Leaves describe a single independently reviewable deliverable. The only additional third-level issues are Cursor support leaves under W7, where mechanical evidence can be gathered without sharing implementation scope.

## Dependency policy

The critical path is W1 → W2/W3 → W4 → W5 → W6 → W7, with leaf-level links reflecting narrower prerequisites. Replacement authority must be proven before consumer migration, every live consumer must migrate before deletion, and retirement/provenance gates must be green before release evidence and sign-off.

Parent-child hierarchy expresses scope; `blocks` and `blocked by` relations express execution order. A parent issue is not automatically complete when one child completes.

## Completion and evidence policy

- OpenSpec checkboxes remain unchecked until their own acceptance evidence exists; Linear status alone never changes normative completion.
- Done issues retain commit SHAs, test totals, and review evidence.
- Mechanical Cursor evidence is reviewed by Codex before it is incorporated into a parent gate.
- CYB-44 may close only after all required predecessors, the three-target matrix, retirement/provenance scans, documentation, GitNexus changed-scope review, and whole-branch review are green.
- Project health remains At risk until the release claim boundary is genuinely crossed.
