## Generic serialization and structural metadata

**Documented facts.** Serde normally derives bounds from the generic types used by serialized/deserialized fields; explicit bounds replace those inferred bounds. Its field attributes permit separate serialize and deserialize constraints. This is a useful precedent for preserving a declaration's real generic obligations instead of changing its public API to accommodate generation. [Serde handwritten bounds](https://serde.rs/attr-bound.html), [Serde field attributes](https://serde.rs/field-attrs.html).

**Beskid inference and remedy.** Implement `impl<T, E> Item<T> : Serializable<E> where E: Encoder` as canonical syntax and semantic facts. Preserve ordered parameters and bounds through AST, formatter, source SDK schema/factories, typed CABI2 contributions, method specialization, and applied contract witnesses. Do not replace `T: Serializable<E>` with a wrapper receiver, erase `E` to a physical pointer, or treat an unapplied template as a concrete `TypeShape`. The separate invocation-issued `TypeTemplate` and private contribution carrier must retain the original source/package/generation proof. At a concrete specialization, issue actual parameter substitutions and applied witnesses from the registered semantic graph.

**Gate WEB-SER01.** Execute a real generic generated implementation with two distinct concrete `T`/`E` pairs; verify the chosen encoder implementation and exact argument identities. Reject missing `Encoder`, wrong applied contract arguments, duplicate/unbound parameters, stale/foreign templates, and a physically identical but nominally different parameter. Parser metadata and SDK mirror tests alone are insufficient.

**Documented facts.** Serde defaults apply when an input field is missing and can come from `Default` or an explicit function. Flattening is limited to named-field structs with a struct/map field; Serde explicitly disallows combining flattening with `deny_unknown_fields`. A flattened map captures additional fields. [Defaults](https://serde.rs/attr-default.html), [Flattening](https://serde.rs/attr-flatten.html).

**Beskid inference and remedy.** Keep default/rename/catchall policies in exact retained field/enum attributes, including payload enums. Resolve default constructors as typed source callables; distinguish absence from an explicit null or malformed value. For catchall, use the existing private exact `Map<string,V>` field witness and source-bound generated contribution correspondence. Unknown fields must validate against `V`, populate that map on decode, and flatten deterministically on encode. Do not copy Serde's blanket flattening policy into the bespoke standard: beskid must define its own closed-versus-issued-catchall rule, duplicate-key behavior, and declared/catchall key collisions.

**Gates WEB-SER02/03.** Real Mod-generated record and payload-enum roundtrips must preserve renamed fields, missing-field defaults, and all payload variants. Wrong default result type, explicit wrong values, duplicate keys, unknown fields without proof, declared/catchall collisions, foreign catchall carriers, and changed source bodies must fail with source spans. Include allocation failure during decode/encode and verify unpublished output or rollback.

## Cargo artifact selection and actual shared linkage

**Documented facts.** Cargo emits line-delimited JSON with `--message-format=json`; `compiler-artifact` identifies package, target, crate types, produced filenames, and profile, while `build-finished` reports success. Output from other tools need not be JSON. `cargo metadata` has a versioned format and callers should request a format version explicitly. [Cargo external tools](https://doc.rust-lang.org/cargo/reference/external-tools.html).

**Beskid inference and remedy.** The Rust Glue producer should parse bounded Cargo messages, match exact package/manifest and requested target/profile with `cdylib`, and select exactly one actual emitted native library. Do not guess `target/debug/lib<name>`, scan stale directories, choose the first shared file, or accept a valid artifact message from a failed build. Preserve diagnostics separately; reject malformed artifact messages affecting the selected target and contradictory/ambiguous matches. Validate the final native image and private producer/source/tool/provider evidence before admission.

**Gate WEB-ART01.** Fixtures must cover hyphenated crate names, multiple packages/artifact kinds, stale neighboring libraries, custom target directory, cross target, release profile, fresh artifacts, noisy non-JSON lines, build failure after an artifact message, and ambiguous matching output. The native fixture must load the exact selected image and call a generated export.

**Documented facts.** Rust `cdylib` is the dynamic system-library format for loading from another language, whereas `dylib` is a Rust dynamic library. `staticlib` incorporates upstream dependencies and can expose additional symbols; the reference calls for export control and inspection of actual linkage where target flags vary. [Rust linkage](https://doc.rust-lang.org/reference/linkage.html).

**Beskid inference and remedy.** Keep the qualified shared-provider linkage explicit. A `cdylib` file extension does not establish a canonical runtime dependency, allocator compatibility, or source ownership. Inspect ELF/Mach-O/PE loader tables and exact exports, retain the private producer-issued admission witness, pin verified images/provider snapshots, and require the installed shared provider; no static fallback. Gate WEB-ART02 must relocate the qualified bundle, load two libraries under one canonical host lease, and reject absent, duplicated, substituted, or wrong-target provider dependencies.

## Ownership and panic behavior at the ABI

**Documented facts.** `Box<T>` owns its allocation. Although a sized box has C-pointer-compatible representation, converting an arbitrary pointer into a box is invalid unless allocation, alignment, value, and allocator obligations hold. Its destructor uses Rust's global allocator. [Rust Box memory layout](https://doc.rust-lang.org/std/boxed/index.html#memory-layout).

**Beskid inference and remedy.** Never reconstruct a Rust box from a managed beskid pointer or an opaque ownership token. Keep source constructors and GC roots for managed SDK values, and route owned byte/string release through the exact library-qualified provider issuer. Borrowed values cannot outlive invocation authority; images must remain pinned until canonical heap destruction. Gate WEB-FFI01 includes foreign/stale/double release, wrong kind/shape/library, allocation failure, and two-library close while managed values remain live.

**Documented facts.** An FFI boundary must explicitly permit unwinding if unwinding is intended. A Rust panic crossing a non-unwind boundary aborts; a foreign exception entering Rust there is undefined behavior. `catch_unwind` handles unwinding Rust panics, not aborts or foreign exceptions. [Rustonomicon FFI unwinding](https://doc.rust-lang.org/nomicon/ffi.html#ffi-and-unwinding).

**Beskid inference and remedy.** Keep the CABI2 boundary non-unwinding and translate recoverable Rust errors before returning. Catch Rust unwinding panics inside Rust exports where recovery is supported; retain worker-process isolation for abort/trap/native faults. Do not claim `catch_unwind` contains a foreign exception or `panic=abort`. Gate WEB-FFI02 runs panic-unwind, panic-abort, trap, malformed callback, cancellation, and subsequent successful invocation, verifying bounded worker reap and no retained invocation authority.

## Cancellation, pipes, and channels

**Documented facts.** Dropping Tokio's child handle normally leaves its process running; kill-on-drop is optional. Unix children require reaping, and Tokio's automatic cleanup is only best effort. The process documentation also warns against sequential pipe writes and exit waits that can deadlock. [Tokio process caveats](https://docs.rs/tokio/latest/tokio/process/index.html#caveats).

**Documented facts.** `start_kill` does not wait; `kill` performs kill plus wait. `wait` is cancellation-safe and closes retained stdin; `try_wait` is nonblocking and reaps an exited Unix child but does not close stdin. [Tokio Child](https://docs.rs/tokio/latest/tokio/process/struct.Child.html).

**Beskid inference and remedy.** Retain one owner until exit settlement, explicitly terminate and reap under one absolute deadline, and concurrently advance bounded stdin/stdout/stderr. A cancelled waiter is not a process-termination proof. Tokio's documented child operations also do not establish descendant-tree cleanup: preserve bespoke Unix process-group/Windows job containment and actual descendant PID tests. Corelib's cooperative fibers must use existing nonblocking probes/parking, not introduce Tokio as another scheduler.

**Gate WEB-PROC01.** On native macOS, Linux x86_64, and Windows x86_64, cancel/timeout during spawn confirmation, partial write, output flood, blocked read, and nested child execution. Verify no active descendants, successful reap, bounded diagnostic memory, exact argv/Unicode env/cwd, repeated close, stale tokens, and explicit cleanup failure. The total protocol acknowledgment plus OS cleanup must use one `min(userDeadline, admissionTime+5s)` cap, not consecutive independent five-second budgets. OS synchronous spawn preemption limitations remain explicit.

**Documented facts.** Tokio's bounded MPSC channel supplies backpressure. Clean shutdown closes admission then drains buffered messages; dropping the receiver discards unread messages. A oneshot carries one completion, and sender disappearance is observable as a receive error. [MPSC](https://docs.rs/tokio/latest/tokio/sync/mpsc/index.html), [Oneshot](https://docs.rs/tokio/latest/tokio/sync/oneshot/index.html).

**Beskid inference and remedy.** Give Glue requests a bounded admission queue, unique pending-ID ownership, and exactly one completion/cancellation settlement. Close admission before draining pending requests; distinguish disconnect, cancellation, timeout, and peer protocol errors. Cache close settlement for aliases and allow only one cleanup/join owner. Gate WEB-CHAN01 fills capacity, drops either endpoint, races response/cancel/deadline, sends late/repeated responses, and closes twice; every waiter settles once and buffered payloads are released. Use beskid's existing channel/fiber runtime.

## Package source identity file set

**Documented facts.** With no `include` or `exclude`, Cargo packages every file under the package root except the root `target/` directory and any subdirectory that holds its own `Cargo.toml`; nested packages are always excluded. The `tests/` directory is packaged by default. Gitignore rules apply only when `include` is absent, and hidden files are dropped outside a git repository. `cargo package --list` shows the exact set. [Cargo manifest include/exclude](https://doc.rust-lang.org/cargo/reference/manifest.html#the-exclude-and-include-fields). Go module zips exclude `go.mod` files in subdirectories (the subtree is its own module), `vendor` directories, VCS directories and symbolic links, and the `h1:` hash recorded in `go.sum` is computed over that module zip file set, so the proof covers exactly what ships. [Go modules reference, module zip files](https://go.dev/ref/mod#zip-files). The documentation fetched here did not restate that the `Cargo.lock` registry checksum covers the packaged `.crate`; treat that as unconfirmed from this session and check the Cargo lockfile documentation before citing it.

**Beskid inference and remedy.** Both toolchains define the shipped set by structure (package root minus build/VCS output minus nested project roots), not by the directory name `tests`. Cargo even ships `tests/`. The proposed shared rule is supported: one function, used by both the proof walker and the materializer, that skips `obj`, `.beskid`, `.git`, `node_modules` and any subdirectory containing a `.bproj`, and ships everything else. Excluding the literal name `tests` in the copier is not supported by either precedent and is what makes the corelib proof and copy disagree, because `tests/corelib_tests/` is a nested project. Preserve the property that the proof covers every file the package actually ships. Decide explicitly, as Go does, whether symbolic links are rejected or skipped, and apply that identically on both sides.

**Gate WEB-SRC01.** One shared file-set function with unit tests: nested `.bproj` subtree excluded from both proof and copy, a non-nested `tests/` directory included in both, build/VCS directories excluded in both, and a corelib fixture whose proof equals the materialized tree byte for byte. A file added to or changed inside the shipped set must change the proof; a file inside a nested project must not.

## Materialized copies with stale files

**Documented facts.** `cargo vendor` removes the existing output directory and recreates it with only the currently needed crates; `--no-delete` is an explicit opt-out that keeps old contents. [cargo vendor](https://doc.rust-lang.org/cargo/commands/cargo-vendor.html). `go mod vendor` rebuilds the `vendor` directory and writes `vendor/modules.txt`. [Go modules reference, go mod vendor](https://go.dev/ref/mod#go-mod-vendor). Cargo's `.cargo-checksum.json` in directory sources guards against accidental modification only and is not a security mechanism. [Source replacement](https://doc.rust-lang.org/cargo/reference/source-replacement.html).

**Beskid inference and remedy.** Both tools recreate rather than merge, so deleted or renamed files cannot linger. Materialize into a fresh sibling staging directory, run the shared-rule proof against the staging tree, then replace the old directory with a rename (same filesystem) so a failure leaves the previous copy intact. Never copy-when-newer into an existing tree. Neither tool documents atomic replacement; the staging-and-rename step is a Beskid decision, not a documented precedent. Because the checksum file is not a security boundary, the proof must remain the authority.

**Gate WEB-SRC02.** Materialize, delete and rename a source file, materialize again, and verify the proof passes and the removed file is absent. Inject a failure mid-copy and verify the previous materialization is unchanged and no staging directory is mistaken for a package.

## Canonical path identity on macOS

**Documented facts.** `std::fs::canonicalize` returns an absolute path with intermediate components normalized and symbolic links resolved; on Unix it uses `realpath`, on Windows it returns an extended-length path. [std::fs::canonicalize](https://doc.rust-lang.org/std/fs/fn.canonicalize.html). The macOS `/var` to `/private/var` link was not re-verified from Apple documentation in this session; it is the known system layout and the observed failure matches it.

**Beskid inference and remedy.** A temporary directory reported as `/var/...` and the same location reported as `/private/var/...` are one identity, so membership and prefix checks must compare canonical paths on both sides. This is already fixed by interning both sides; the fact is recorded here. On Windows, canonical output carries the extended-length prefix, so compare only canonical-to-canonical and never mix raw and canonical forms in prefix tests.

**Gate WEB-PATH01.** Retain a regression test that creates a root through a symlinked parent and verifies membership succeeds from both spellings, plus a negative case where a symlink escapes the root.

## Build-receipt profile binding

**Documented facts.** Profile settings are read only from the workspace root manifest; settings in dependencies are ignored. `[profile.dev.package."*"]` is the override for dependency packages, and the profiles page describes `*` as matching non-workspace-member dependencies, so workspace members take their settings from `[profile.dev]` or `[profile.release]` unless named explicitly. `dev` is the default for `cargo build` and `release` for `--release`. [Cargo profiles](https://doc.rust-lang.org/cargo/reference/profiles.html). The `compiler-artifact` JSON message carries the profile used, including `opt_level`. [Cargo external tools](https://doc.rust-lang.org/cargo/reference/external-tools.html#json-messages). The fetched profiles summary phrased the wildcard as all dependencies; the member exclusion is from the full reference text and should be re-read when the gate is written.

**Beskid inference and remedy.** The qualifier should bind the expected `opt_level` of each workspace-member artifact to the declared workspace profile for the requested build (dev or release), not to a hard-coded constant and not to a dependency override. The documented facts support this. Dependency artifacts may legitimately differ through the `"*"` override and must not be held to the member value. This is already applied in `scripts/ci/qualify-native-tool-driver.py`.

**Gate WEB-PROF01.** Fixtures with a workspace `[profile.dev]` opt-level, a `"*"` dependency override, and a named per-package override; a member artifact with a mismatched `opt_level` must be rejected, a dependency with the override value accepted, and a changed workspace profile must change the expected value.

## Rust Glue build inputs for `beskid build`

**Documented facts.** Binding tools split declaration by kind of information. maturin keeps the crate location and build policy in the project manifest: `[tool.maturin]` has `manifest-path`, `module-name`, `bindings`, `profile` and `locked`/`frozen`, and the module name defaults to the Cargo package name. [maturin configuration](https://www.maturin.rs/config.html). napi-rs keeps `binaryName`, `packageName` and `targets` in package configuration, and declares exported items with `#[napi]` in source. [napi config](https://napi.rs/docs/cli/napi-config). UniFFI declares exports with `#[uniffi::export]` and object types with `uniffi::Object` in source. A function that returns `Result<T, E>` is fallible: the foreign function returns `T` and throws on `Err`. [UniFFI proc macros](https://mozilla.github.io/uniffi-rs/latest/proc_macro/index.html), [UniFFI errors](https://mozilla.github.io/uniffi-rs/latest/proc_macro/errors.html). cxx declares opaque Rust types and functions in the bridge declaration. Those names "refer to types in the `super` module" through ordinary scope. A bridge `Result<T>` gives only the Ok type and marks the function fallible. A panic in an `extern "Rust"` function aborts the process. [cxx extern Rust](https://cxx.rs/extern-rust.html), [cxx Result](https://cxx.rs/binding/result.html). cbindgen selects items from source markers (`#[no_mangle] pub extern fn`). `cbindgen.toml` only adds includes, exclusions and renames. [cbindgen docs](https://github.com/mozilla/cbindgen/blob/master/docs.md). Cargo: a `[lib]` name defaults to the package name with dashes changed to underscores, and `crate-type = ["cdylib"]` selects the C dynamic library form. [Cargo targets](https://doc.rust-lang.org/cargo/reference/cargo-targets.html). `--locked` fails if `Cargo.lock` is missing or would change. `--offline` prevents all network access. [cargo build](https://doc.rust-lang.org/cargo/commands/cargo-build.html). Tool selection in Cargo is ambient by default. The `RUSTC` environment variable replaces the compiler. `RUSTC_WRAPPER`/`RUSTC_WORKSPACE_WRAPPER` wrap it. Cargo sets `CARGO` for build scripts. `CARGO_HOME` moves the cache and the home config. `CARGO_BUILD_*`-style variables override config keys. `CARGO_ENCODED_RUSTFLAGS` has priority over `RUSTFLAGS`, `target.<triple>.rustflags` and `build.rustflags`. [Cargo environment variables](https://doc.rust-lang.org/cargo/reference/environment-variables.html). Cargo merges `.cargo/config.toml` from the current directory, every ancestor and `$CARGO_HOME/config.toml`. Precedence is `--config`, then environment, then files, and `target.<triple>.linker` sets `-C linker`. [Cargo config](https://doc.rust-lang.org/cargo/reference/config.html). rustup proxies choose a toolchain from `+toolchain`, `RUSTUP_TOOLCHAIN`, directory overrides, the nearest `rust-toolchain.toml`, then the default. [rustup overrides](https://rust-lang.github.io/rustup/overrides.html).

**Beskid inference and remedy.** The precedents agree on three things. (1) The project manifest names the native library and the location of the binding crate (maturin, napi-rs). (2) Item-level mappings live next to the declaration that the generator reads (UniFFI, napi-rs, cxx), not in a separate mapping file. (3) Fallibility is part of that declared signature (UniFFI, cxx). In Beskid, the Extern contract and the `GlueHandle` type are that declaration, so the mappings belong in Beskid source.

Remedy: add one top-level manifest block, `glue "<library>" { backend = rust path = "<dir>" }`. Its label is the owner's native library identity and must equal an `Extern`/`GlueHandle` `Library` string. `path` is a project-relative directory of `.rs` files with `implementation.rs` as the entry. The consumer library identity is the target name, the same default stem as the output; this follows Cargo's lib-name default. Mappings use a closed source attribute `RustOwner`:
- On a `GlueHandle` type, `Path` is required.
- On an Extern contract method, `Path` and `Fallible` are optional. The defaults are `implementation::<symbol>` and `false`, following cxx's implicit resolution in one fixed scope.

Every path must start with `implementation`. Without this rule, a path such as `std::process::abort` would type-check.

0.6 has no third-party crate dependencies. The producer generates `Cargo.toml` and `Cargo.lock` and runs `--offline --locked`. A user `Cargo.toml`, `Cargo.lock`, `build.rs`, non-`.rs` file or symlink in `path` is rejected and never silently ignored. A later dependency-capable form should follow maturin's `manifest-path` plus a locked build. Tool paths are machine-local, and Cargo keeps them out of `Cargo.toml` too. Beskid therefore takes them only from `beskid build` flags: `--rust-toolchain <prefix>`, or `--cargo` and `--rustc` together, plus a required `--linker`. Beskid never reads `CARGO`, `RUSTC` or `PATH` to select them. Cargo itself exports `CARGO`/`RUSTC` to children, so reading them would capture a tool silently whenever beskid runs under Cargo.

Ambient Cargo configuration can change the build without changing recorded inputs. The current producer stages under the output parent and inherits the environment. The owner build must therefore:
- remove inherited `CARGO_*`, `RUSTFLAGS`, `RUSTDOCFLAGS`, `RUSTC_*` and `RUSTUP_TOOLCHAIN` before setting its own values;
- point `CARGO_HOME` at an empty staged directory;
- reject any ancestor `.cargo/config` or `.cargo/config.toml` of the staging directory, because `--config` can override keys but cannot remove them;
- reject any ancestor `rust-toolchain`/`rust-toolchain.toml` when the selected cargo is used through a rustup proxy.

Both of these last rejections are Beskid decisions. Neither tool documents a switch that disables discovery. `glue-dotnet` keeps failing closed.

## How published Glue images find the shared runtime provider

**Spec.** The change spec fixes only the provider identity. Mach-O uses `@rpath/<canonical dylib basename>`, ELF uses a basename-only `DT_SONAME`, and PE/COFF keeps the canonical DLL basename in the import library. The loader must then resolve "the canonical installed provider through its target loader search mechanism" without requesting a deleted staging path (`execution--runtime--panic-io-and-syscalls`, "Relocatable canonical shared provider identity"). The spec does not say how a consumer or owner image supplies that search path. The decision below follows the platform documentation.

**Documented facts.**
- Apple dyld: an install name that starts with `@rpath/` is resolved against the `LC_RPATH` entries of the loading image and of the images that loaded it. The relocatable library carries the `@rpath` ID, and the loading image supplies the run path. [Run-path dependent libraries](https://developer.apple.com/library/archive/documentation/DeveloperTools/Conceptual/DynamicLibraries/100-Articles/RunpathDependentLibraries.html), [Embedding nonstandard code structures](https://developer.apple.com/documentation/xcode/embedding-nonstandard-code-structures-in-a-bundle).
- ELF `ld.so`: a dependency name without a slash is searched in `DT_RUNPATH` of the requesting object. `DT_RUNPATH` applies only to the direct dependencies of that object. `$ORIGIN` expands to the directory of the object, so that unpacked trees can find their own libraries. [ld.so(8)](https://man7.org/linux/man-pages/man8/ld.so.8.html).
- Windows: dependencies of a DLL are searched "as if they were loaded by using only their module names", even when the first DLL was loaded by a full path. Before any directory is searched, the loader checks the loaded-module list: "whether a DLL with the same module name is already loaded into memory (no matter which folder it was loaded from)". The directory of the requesting DLL is searched only with `LOAD_WITH_ALTERED_SEARCH_PATH` or `LOAD_LIBRARY_SEARCH_DLL_LOAD_DIR`. A host can add a directory with `AddDllDirectory` plus `LOAD_LIBRARY_SEARCH_USER_DIRS`, or with `SetDllDirectory`. [Dynamic-link library search order](https://learn.microsoft.com/en-us/windows/win32/dlls/dynamic-link-library-search-order).

**Beskid decision.** The spec requires the *installed* canonical provider. A copy of the provider beside the published images would be a second, uninstalled provider, so it is not used. `$ORIGIN`/`@loader_path` run paths are not used either, because they would find such copies.
- macOS and Linux: the producers link each consumer image (`unix_link_command`, `GlueSharedProviderV1`) and each Rust owner image (`build_rust_owner`, `-C link-arg=-Wl,-rpath,...`) with one absolute run path: the shared directory of the validated installed kit. The provider dependency is `@rpath/libbeskid_runtime.dylib` (Mach-O) or the provider basename (ELF), and the producers reject any other runtime dependency. The kit dylib itself keeps its `@rpath` ID and no `LC_RPATH` (Gate WEB-KIT01), so kit hashing stays exact. `beskid build --backend glue-rust` publishes these images unchanged. Staging paths never reach the loader tables, because the run path names the installed kit and the provider identity is a basename.
- Windows: the image imports the canonical DLL basename. The Beskid Glue loader pins the validated installed provider by full path before it loads any Glue image, so the loaded-module list satisfies the import. A foreign host must put the installed kit's shared directory on its DLL search path (`AddDllDirectory` with `LOAD_LIBRARY_SEARCH_USER_DIRS`), or load the provider first. The CLI does not copy the provider.
- A published image is therefore bound to the installed toolchain prefix that built it. Images that move to another machine or prefix are not supported in 0.6. A later relocatable form needs a reviewed provider-placement rule, not an implicit copy.

**Gate WEB-GLUE02.**
- Interop harness, all three native hosts: run the qualified installed `beskid build --backend glue-rust` alone on `fixtures/glue/manual/owned` (`v06_glue_cli_builds_owned_fixture_alone`). After the staging directory is gone, both published images must be native images. On macOS and Linux each image must carry the installed kit shared directory as its run path. No staging entry may remain beside the outputs.
- The same harness must show that inherited `RUSTC`, `CARGO`, `RUSTC_WRAPPER`, `RUSTUP_TOOLCHAIN`, `RUSTFLAGS`, `CARGO_BUILD_RUSTFLAGS` and `CARGO_ENCODED_RUSTFLAGS` have no effect. An ancestor `.cargo/config.toml` of the owner staging directory must be rejected with no output. A rebuild must replace both images, and a failed rebuild must leave both images byte-identical.

## Admission of published Glue images

**Spec.** The scenario "Owned fixture builds through the CLI alone" requires that the published consumer and owner images give loaded calls that match the manual results. Before this change, only the in-process route could initialize a process, because initialization needs the private producer witness (checked entries, failure admissions, Dynamic shapes, opaque transports, source generation). The release principle is that no mutable sidecar grants trust. Admission must bind exact image bytes and producer, source, tool and provider evidence, and must fail closed on substitution.

**Documented facts.**
- rustc stores crate metadata inside the artifact: in `lib.rmeta` for an rlib, and "in a special link section called `.rustc`" for a dylib. The SVH makes sure that "the correct crate dependencies are loaded". It is a consistency check, not a security boundary. [Libraries and metadata](https://rustc-dev-guide.rust-lang.org/backend/libs-and-metadata.html).
- Python `RECORD` lists every installed file with an optional hash. The `RECORD` file itself has an empty hash, so the record cannot vouch for itself. [Recording installed projects](https://packaging.python.org/en/latest/specifications/recording-installed-packages/).
- pip hash-checking mode takes the expected hashes from the requirements file, which the user controls, and stops the install on a mismatch. [Secure installs](https://pip.pypa.io/en/stable/topics/secure-installs/).
- fs-verity "by itself ... only provides integrity protection". To authenticate a file, "you must verify the authenticity of the 'fs-verity file digest'" against a trusted value or signature. [fs-verity](https://docs.kernel.org/filesystems/fsverity.html).
- .NET: "Do not rely on strong names for security. They provide a unique identity only." .NET 5+ does not validate the strong-name signature. [Strong-named assemblies](https://learn.microsoft.com/en-us/dotnet/standard/assembly/strong-named).
- Apple silicon requires a signature on all code. `ld` signs at link time, and tools that change a binary after linking must re-sign it ([Big Sur universal apps release notes](https://developer.apple.com/documentation/macos-release-notes/macos-big-sur-11_0_1-universal-apps-release-notes), cited in Gate WEB-KIT01).

**Beskid decision.** Embed evidence before the link, and take trust from one host-supplied digest.
- Each producer compiles an admission record into its image before the link, like rustc `.rustc` metadata. The consumer record is a generated C object (`admission_record.o`). The owner record is a generated `owner_admission.rs` module of the bridge crate. The record is an exported read-only data symbol with a 24-byte frame (magic `BESKID-GLUE-ADM1` and a little-endian length) and canonical JSON. The loader finds it through the export table and reads it from the file bytes. No image code runs during admission. Because the record exists before the link, the platform linker signature covers it, and no image is patched afterwards.
- The consumer record holds the compiler identity (`beskid_aot/<version>`), library, source generation, the full Glue packet, provider digest and loader identity, body/adapter object digests, adapter source and compiler digests, the private producer closure, and one `(library, image sha256)` pin for each owner. Owners are produced before the consumer, so these pins are final. The owner record holds the library, generation, provider, source digest and inventory (all inputs except the record file), the cargo/rustc/linker/driver digests, the destructor and checked-export closure, and the export list. Each producer reads the record back from its linked image and fails if it differs from the issued record.
- A record is evidence, not trust. Anyone who can rewrite an image can also rewrite its record (SVH, RECORD and strong-name precedent). The trust root is therefore the consumer SHA-256 that the host supplies, as in pip hash-checking and fs-verity. `beskid build --backend glue-rust` prints `sha256 <digest>  <path>` for each published image, as part of its own result output. `admit_published_glue_images(PublishedGlueRequest { runtime, consumer, consumer_sha256, owners })` checks the consumer digest, then admits each owner only if its exact digest is pinned in the consumer record. The provider comes from the validated installed kit (`prepare_runtime`). Each owner's driver digest must equal the digest of `<prefix>/bin/beskid_native_tool_driver`. This is consistent with Gate WEB-GLUE02, which binds a published image to the installed prefix that built it. After these checks, admission uses the same `GlueProcess` initialization as the in-process route (`open_issued`, `attach_issued_owner`).
- Rejected: a digest over the image without the record region, stored in the record. The record would then vouch for itself, which detects only accidental corruption. Writing the record into a linked image also breaks the Mach-O linker signature, which would need re-signing. Rejected: a toolchain-local admission store under the installed prefix, keyed by image digest. It is mutable state that a build writes into a prefix that is often read-only (Homebrew, system packages). It is still a sidecar, only in another place. Rejected: trusting the record's own compiler-driver identity alone, because the record cannot authenticate itself.
- Owner Windows format check: `build_rust_owner` expected `BinaryFormat::Coff` for a DLL, but the `object` crate reports PE images as `BinaryFormat::Pe`, so every Windows owner was rejected. The check now expects `Pe`.

**Gate WEB-GLUE03.**

## Deterministic map and catchall encoding (serialization Mod)

**Documented facts.** Go `encoding/json` `Marshal` sorts map keys: "The map keys are sorted and used as JSON object keys", so output does not depend on the runtime map layout. [encoding/json](https://pkg.go.dev/encoding/json). serde_json writes a map in the iteration order of the map it is given. Its own `Map` is kept "always ... in a sorted state" unless the `preserve_order` feature selects an insertion-ordered backing. [serde_json Map](https://docs.rs/serde_json/latest/serde_json/struct.Map.html). Rust `HashMap::keys` and `iter` visit entries "in arbitrary order", so a HashMap serialized through serde has no stable key order. [std HashMap](https://doc.rust-lang.org/std/collections/struct.HashMap.html). RFC 3629 section 1: "The byte-value lexicographic sorting order of UTF-8 strings is the same as if ordered by character numbers." [RFC 3629](https://www.rfc-editor.org/rfc/rfc3629).

**Beskid inference and remedy.** Foundation `Map` is an insertion-ordered linear entry array, and `Remove` shifts entries, so its layout is a history of edits, not a stable order. Encoding in that order would make equal maps produce different bytes. Beskid follows Go: deterministic output sorts keys at encode time, independent of the map's internal layout. The order is ordinal: byte-wise UTF-8 comparison, which RFC 3629 makes equal to code point order and which needs no locale or collation table.

Remedy:
- Foundation `Map` gains `pub TKey[] Keys()`, a fresh array in entry order that later map mutation does not change.
- `Core.String` gains `CompareOrdinal(string, string)` and `SortOrdinal(string[])`, a stable sort that returns a new array and leaves its input unchanged.
- A generated `Map<string,V>` field writes `BeginMap(count)`, then `BeginMapEntry(key)`/value/`EndMapEntry` for each key in ordinal order.
- A catchall `Map<string,V>` field is encoded by default. Its entries are flattened into the record after the declared fields, in ordinal key order, and the record field count is the declared count plus the catchall count. An entry key equal to any declared wire name fails the write with `CatchallCollision`, because on decode that key would bind to the declared field, not the catchall. `SkipSerialize` on a catchall stays optional.

**Gate WEB-SER04.** Foundation tests must cover `Keys()` on an empty map, key order and contents after insert/update/remove, an unchanged `Keys()` result after later `Insert`/`Remove`, and `SortOrdinal` on mixed ASCII, prefix and multi-byte UTF-8 keys. Mod generation tests must show that a `Map<string,V>` field and an encoded catchall now produce `WriteTyped`, that the generated body sorts keys through the issued `Core.String.Core.SortOrdinal` route, that the catchall loop follows the declared fields, and that the collision check and the dynamic field count are generated.

**Local evidence.** Homebrew 0.5.2 install on macOS arm64 fails every compile with `ArtifactHashMismatch` for `release/shared/libbeskid_runtime.dylib` (expected `19802e88…`, actual `b61fd40c…`). Evidence:

Its `LC_ID_DYLIB` is the absolute staging path `/var/folders/…/T/beskid-native-runtime-58018-release-1790961636526615000-0/libbeskid_runtime.dylib`. Its signature is `flags=0x20002(adhoc,linker-signed)` and `Identifier=libbeskid_runtime.dylib`.
- In the installed keg, `LC_ID_DYLIB` is `/opt/homebrew/opt/beskid/libexec/lib/beskid-runtime/abi-5/aarch64-apple-darwin/release/shared/libbeskid_runtime.dylib`. **Documented facts.** Homebrew source (Homebrew 7.0.7, `Library/Homebrew/extend/os/mac/keg_relocate.rb`, `formula_installer.rb`):
- `FormulaInstaller#finish` calls `fix_dynamic_linkage` for every install that is not a poured bottle with `skip_relocation`. Source and prebuilt-archive installs therefore always run it.
- `fix_dynamic_linkage` sets the ID of every keg dylib to `dylib_id_for(file)`, which is `opt_record/<relative dir>/<basename>`. There are only two exceptions: `/usr/lib/swift/libswift*`, and IDs that start with `@rpath` when the formula declares `preserve_rpath`. Dependency names and run paths that start with `@` are filtered out (`VARIABLE_REFERENCE_RX`). Absolute dependency names are kept unless they are rooted in the build temp directory. Absolute run paths that are duplicates or rooted in the build directory are deleted.
- `change_dylib_id`, `change_install_name` and `change_rpath` return early when old and new names are equal. Only files that were actually modified are saved and passed to `codesign_patched_binaries`. **An unmodified file is not re-signed and its bytes stay exact.**
- The cleaner only fixes permissions and prunes files under `prefix/bin`, `sbin` and `lib`, not `libexec`. It does not change file contents.
- `preserve_rpath` was added on 2025-10-02 and first shipped in Homebrew 4.6.17. Its public documentation reads "Preserve `@rpath` install names when fixing dynamic linkage on macOS." [Formula#preserve_rpath](https://docs.brew.sh/rubydoc/Formula.html). The in-source doc adds that by default Homebrew rewrites install names, including `@rpath` ones, to absolute paths.
- Bottle relocation applies only to keg references. `:any_skip_relocation` bottles "did not contain any references to the Cellar". [Bottles](https://docs.brew.sh/Bottles).

Apple: on Apple silicon "any executable must be signed before it's allowed to run", and an ad-hoc signature is enough. `clang`/`ld` sign automatically. Tools that modify a binary after linking ("e.g. `strip` or `install_name_tool`") require re-signing. [Big Sur universal apps release notes](https://developer.apple.com/documentation/macos-release-notes/macos-big-sur-11_0_1-universal-apps-release-notes). A relocatable library has an `@rpath/<name>` ID, and the loading image supplies `LC_RPATH`. [Embedding nonstandard code structures](https://developer.apple.com/documentation/xcode/embedding-nonstandard-code-structures-in-a-bundle).

**Beskid inference and remedy.** The cause is confirmed. The kit dylib had an absolute staging ID. Homebrew rewrote it to the opt path, which invalidated the linker signature, and then re-signed the file ad hoc. Both steps change raw bytes. An `@rpath` ID alone is not enough, because Homebrew also rewrites `@rpath` IDs unless the formula declares `preserve_rpath`. The remedy keeps exact raw-byte hashing and needs no canonical Mach-O digest. With both conditions below, every Homebrew name comparison is equal, the file is never saved, and it is never re-signed:
1. Link the kit shared runtime with `-Wl,-install_name,@rpath/libbeskid_runtime.dylib`, no `LC_RPATH`, and only absolute `/usr/lib/` or `/System/Library/` dependencies. The release worktree already carries this flag as an uncommitted change in `compiler/crates/beskid_aot/src/linker/orchestration.rs` (`unix_link_command`, SharedLib on darwin), and `beskid_aot/tests/library_pair.rs` asserts `@rpath/` on the linked pair. Consumers already get `-Wl,-rpath,<validated kit shared dir>` (`GlueSharedProviderV1`).
2. Declare `preserve_rpath` in the Homebrew formula, and require Homebrew 4.6.17 or later.

The rejected alternative is a canonical Mach-O digest that skips `LC_CODE_SIGNATURE` and the install-name and run-path strings. It would accept a file whose ID and signature Homebrew chose, and it would lose the signature as part of the bound identity. It would also need a Mach-O parser in the verifier. Because Homebrew does not touch unmodified files, this weakening is not needed. A kit that Homebrew relocates must still fail closed. `skip_clean` does not help, because it controls the cleaner, not linkage fixing.

## Checking an `Aggregate` project

**Local evidence.** An entry-less `Lib` assembly now roots every unit of the host source root (`AssemblyRootSet::OwnUnits`). An `Aggregate` manifest such as `compiler/corelib/beskid_corelib/corelib.bproj` has `type = Aggregate`, no own source tree (`root` defaults to the empty string), and a placeholder `__aggregate__` Lib target with no entry. Its own-unit set is therefore empty, and `beskid check` failed with `NoRootUnits`.

**Documented facts.** A Cargo manifest with `[workspace]` and no `[package]` is a virtual manifest. In a virtual workspace, "all members will be used (as if `--workspace` were specified on the command-line)". Path dependencies that reside in the workspace directory automatically become members. [Cargo workspaces](https://doc.rust-lang.org/cargo/reference/workspaces.html).

**Beskid inference and remedy.** An `Aggregate` is the Beskid form of a virtual manifest, so checking it checks its members. Members are the direct `source = path` dependencies of the aggregate manifest, in declaration order. Registry and git dependencies are never members. A path member that the compile plan does not carry as a source dependency (`Template`, `Bsol`) has no Beskid source and adds no roots. The root set is the own units of each member source root, without units under another effective root nested inside it. Each root keeps its member package identity (`package_for_unit` assigns it from the member root), so it is judged with that member's semantics. Transitive dependencies of members are not roots. A non-aggregate entry-less target with no own units still fails with `NoRootUnits`. An aggregate whose members hold no units fails with `NoAggregateMemberUnits`. A manifest that cannot be read, or a member whose effective root cannot be identified unambiguously, fails with `AggregateMembers`. Unlike Cargo, Beskid does not require members to reside under the aggregate directory, because corelib members are siblings (`../packages/*`).

**Gate WEB-ROOT01.** Loader tests (`beskid_analysis` `projects::assembly::loader::tests`): an aggregate with members `alpha` (two units) and `beta`, a registry dependency, and a transitive path dependency `shared` roots exactly the three member units, in manifest order, and does not root `shared`. An aggregate whose members are empty fails with `NoAggregateMemberUnits`. A host manifest with no own units still fails with `NoRootUnits`. Release check: `beskid check --project compiler/corelib/beskid_corelib/corelib.bproj` reports member diagnostics and does not report `NoRootUnits`.

## Library output emission and export set

**Local evidence.** `beskid build` lowered every non-executable output through `lower_prepared_syntax_module`. That function emits every function body of every assembled unit, dependencies included. For an entry-less `Lib`, the workspace scan assembles every dependency unit, so the whole dependency tree was emitted. The artifact export list held the `[Export]` items of every emitted unit, so a dependency's own `[Export]` declarations were exported from the consumer. The non-entry own units were already emitted. The defect was what got emitted and exported beside them, not missing own units.

**Documented facts.** The Beskid standard says that user export symbols are generated from Beskid compilation units, and that `[Export]` applies to `pub` function definitions with FFI-permitted types (`openspec/specs/language-meta--interop--export-and-callbacks/spec.md`, D-LMETA-EXPORT-0002 and 0003). No normative text exports a `pub` function without `[Export]`, because such a function has no stable C symbol. Rust `staticlib` output contains the local crate's code "along with all upstream dependencies". A library linked from it "exports all public symbols of them", and the reference says that this needs special care. [Rust linkage](https://doc.rust-lang.org/reference/linkage.html). In Rust, `no_mangle` causes the symbol to be publicly exported from the produced library or object file. [Rust ABI](https://doc.rust-lang.org/reference/abi.html).

**Beskid inference and remedy.** A library output owns the units that `ProgramAssembly::library_unit_indices` names. For an entry-less library or aggregate, these are the root units. For a target with an entry, they are the entry plus the units of the host's own source root. Every executable item of the owned units is emitted. A dependency item is emitted only when direct-call reachability from an owned item reaches it. Emission is a union over a key set, so a dependency that several owned units share is emitted once. The export set is the `[Export]` declarations of the owned units only. This is the explicit `no_mangle`-style surface. It avoids the Rust `staticlib` problem, where re-exported dependency symbols must be filtered after the fact. A `pub` item without `[Export]` is emitted but is not part of the C export set. Emission and export order follow assembly order (deterministic workspace scan or import discovery order). Incomplete reachability facts fail the build closed. The AOT `PublicOnly` fallback for an artifact with no `[Export]` entries is unchanged here and is still a separate open question.

**Gate WEB-LIB01.** `beskid_codegen` `library_emission`: an entry-less library with two own units that both call one dependency function emits each own item once and the shared dependency function once. It does not emit unreached dependency items or a dependency `[Export]`. It exports `alpha_answer` and `beta_answer` in that order, and a second lowering is identical. `beskid_aot` `library_emission`: a library with an entry exports the `[Export]` of an imported own unit that the entry does not call. `beskid_cli` `library_target::entry_less_library_exports_declarations_from_every_own_unit`: the shared and static outputs of an entry-less two-unit library expose both exports in `nm`.
