## Standalone behavior that must also change

1. `validate/constraints.rs:46` uses substring/digit heuristics rather than the required supported regex contract; invalid and unsupported patterns do not reliably reject. Establish supported syntax explicitly and run the same pattern corpus in Rust and native implementations.
2. `compose.rs:64` replaces conflicting fields/nested definitions; incompatible conflicts must reject with two definition locations under the approved composition requirement.
3. `semantic.rs:19` collapses duplicate identities into a HashMap and `ensure_ref_resolves` accepts any candidate. Duplicate and ambiguous unqualified identities need explicit diagnostics.
4. `migrate.rs:101` uses whole-source substring replacement and final-brace insertion. Migrations must operate on parsed structure and preserve unrelated source/comment/string bytes.
5. Original `load/fields.rs` conditional map gap and typed-default materialization defect received paired RED tests and Rust fixes; parent reports the 27-test schema/analysis/facade regression gate GREEN. Full actual-profile validation still requires its own corpus.
6. Default materialization in `validate/block.rs:242` is textual and must satisfy the new type-checked missing-only value/default contract. Pattern, default and reference improvements need paired Rust/native tests, not native-only expectations.

## Native implementation hardening before qualification

`Schema.bd` property helpers currently return fallbacks for malformed property shapes; profile validation must reject wrong scalar/list/Boolean forms rather than silently applying defaults. Duplicate scans and rule selection are quadratic; add an explicit bounded work budget or checked indexed lookup before adversarial large inputs. `Validate` re-establishes authority by parsing owned source, so synthetically constructed document mutations are discarded: future migration/typed configuration must first publish a valid owned syntax result through the canonical writer and preserve binding/diagnostic identity, or introduce a checked native syntax authority API. These are real remaining design obligations, not completed guarantees.

## Explicit import host contract draft

Follow existing native contract syntax (`Core.Bytes.ByteReader` and its `BufferReader` implementation), not raw function pointers. Proposed `Core.Bsol.Imports` exposes Source::File(path), Git(url,revision,path), Registry(package,exactVersion,path), Pckg(reference); Request{source,profileName,alias,importerIdentity,span}; MaterializedSource{source,canonicalIdentity,sha256,provenance}; Provenance{controlledRootIdentity,artifactIdentity,lockedRevision,exactVersion,relativePath}; HostError{code,message}; Resolver contract `Result<MaterializedSource,HostError> Resolve(Request request)`. `Schema.LoadProfile<R>(Syntax.Document document,R resolver,limits) where R: Imports.Resolver` drives this checked adapter. The same interface must be used by the eventual Tools materialization host. These public provenance strings are diagnostic records, not independently sufficient production filesystem/lock proof; only host materialization authority can attest realpath, controlled root, immutable locked artifact and cache.

Test adapter uses an owned deterministic fixture table, never filesystem/network access. Request-spanned missing-cache response; source SHA256 mismatch; duplicate aliases; canonical identity with different digest; identical import diamond; import cycle and bounded closure; exact versions/immutable revision/path safety rejected before publication. No SHA256 primitive exists in current Corelib source inventory; a native bounded SHA256 module or approved existing host digest verification authority is necessary before claiming source/digest validation. Source-only import API tests remain a draft until names are frozen and a fresh runner is available. Production host tests for symlink/root escapes and actual locked file/git/registry cache remain mandatory and cannot be replaced by the fixture adapter.
