# v0.6 dependency transaction milestone

The pure transaction receives planned original and replacement bytes; dependency resolution remains the planner's responsibility. An exclusive `fs2` guard protects a colocated private journal. The journal records both original files, replacement bytes and file identities before either public replacement. Recovery validates the project identity and both current files before restoring; unrecognized bytes or replacement identities fail closed. An absent original lock remains absent after rollback.

This verifies the Unix/macOS implementation and injected failure/recovery cases; Windows remains pending.

## Windows backend research and remaining obligations

The current Windows path is incomplete: owner checking is not implemented, and its read-only directory handle does not meet the documented write-access requirement of [FlushFileBuffers](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers). A Windows implementation must not silently swallow that failure.

A proposed backend uses same-volume [MoveFileExW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw) replacement with `MOVEFILE_WRITE_THROUGH`, without `MOVEFILE_COPY_ALLOWED`, plus writable staged-file flushes. The documentation's write-through guarantee needs explicit review for the journal discovery and cleanup protocol; Unix directory fsync cannot simply be renamed into a Windows no-op. [ReplaceFileW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew) preserves destination ACLs, but its write-through flag is explicitly unsupported and failure states require additional recovery handling.

Private state must be created with a protected current-user DACL supplied at creation, and existing private state must be checked using handle-based [GetSecurityInfo](https://learn.microsoft.com/en-us/windows/win32/api/aclapi/nf-aclapi-getsecurityinfo) against the process token user. Public replacement must preserve existing owner/DACL; a new lock must receive the project public-file policy rather than the private journal ACL. Root owns coordination of the target-specific Windows dependency and native backend seam.

Actual Windows acceptance requires private owner/DACL checks, inherited broad-ACL rejection, public ACL preservation, sharing/read-only failures, long Unicode paths, existing/absent locks, same-volume enforcement, concurrent writes, and subprocess interruption at each replacement and committed-marker boundary. macOS verification cannot establish these obligations.
