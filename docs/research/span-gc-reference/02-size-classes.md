# 02. Size classes and the tiny allocator

Part of the [span GC component reference](README.md). Previous: [01 Address space](01-address-space-and-pages.md). Next: [03 Spans](03-spans.md).

## Purpose

Bound internal fragmentation and give every span a single object size so that: the object index and base of any address are arithmetic (no per-object header needed to find boundaries); mark and allocation bits are dense per-slot bitmaps; and free-slot search is a `ctz` over a bitmap word.

## Data structures

Go's generated table (`internal/runtime/gc/sizeclasses.go`, produced by `mksizeclasses.go`):

```
NumSizeClasses = 68        // class 0 = "large object, own span"
MaxSmallSize   = 32768
SmallSizeDiv   = 8         // granularity of the lookup below 1024
SmallSizeMax   = 1024
LargeSizeDiv   = 128       // granularity of the lookup from 1024 to 32768
TinySize       = 16
TinySizeClass  = 2

SizeClassToSize     [68]uint16   // 0, 8, 16, 24, 32, 48, 64, 80, 96, 112, 128, 144, ..., 28672, 32768
SizeClassToNPages   [68]uint8    // pages per span for that class (1 for most; up to 10)
SizeClassToDivMagic [68]uint32   // ^uint32(0)/size + 1; objIndex = ((p-base) * magic) >> 32
SizeToSizeClass8    [1024/8 + 1]uint8         // index divRoundUp(size, 8)
SizeToSizeClass128  [(32768-1024)/128 + 1]uint8 // index divRoundUp(size-1024, 128)
```

The table header lists, per class: bytes per object, bytes per span, objects per span, tail waste, max waste, min alignment. Examples from the generated comment: class 5 is 48 bytes, 170 objects per 8 KiB span, 32 bytes tail waste, 31.52% max waste; class 35 is 1408 bytes on a 16 KiB span, 11 objects, 896 bytes tail waste, 14.00% max waste; class 67 is 32768 bytes, one object per 32 KiB span. Alignment guarantees are stepped: 8 bytes up to 32, 16 up to 256, 32 up to 512, 64 up to 768, 128 above (table "alignment / bits / min obj size").

**Span class** packs size class and a noscan bit: `numSpanClasses = gc.NumSizeClasses << 1` (`runtime/mheap.go:585`), `spanClass = sizeclass << 1 | noscan`. Pointer-free objects of a given size live on different spans than pointer-bearing ones.

## Algorithm

```
sizeToClass(size):                         # runtime/msize.go, malloc.go
    if size <= 1024: return SizeToSizeClass8[divRoundUp(size, 8)]
    else:            return SizeToSizeClass128[divRoundUp(size - 1024, 128)]

roundupsize(size, noscan):                 # runtime/msize.go
    if size <= MaxSmallSize - MallocHeaderSize (or noscan and <= MaxSmallSize):
        return SizeClassToSize[sizeToClass(size)]   # header space is added for scan objects > 512
    return alignUp(size, pageSize)         # large object

objIndex(s, p):                            # runtime/mbitmap.go:1209-1230
    return ((p - s.base()) * s.divMul) >> 32     # exact for offsets < npages*8 KiB
```

**Tiny allocator** (`runtime/malloc.go`, "Tiny allocator" comment; `mallocgcTiny` at line 1202): a noscan request smaller than 16 bytes is carved from a 16-byte block cached in `mcache.tiny`/`tinyoffset`; the block is a normal class-2 object and is freed when every sub-object in it is dead. The comment names small strings and single-value interface boxes as the beneficiaries. Consequences: a tiny object can be kept alive by a co-located neighbor (`runtime/mfinal.go:389-395` on finalizers), and Go 1.26 refuses the tiny path for goroutines in "secret" mode so sensitive bytes are not retained (`runtime/malloc.go:1136-1141`, go.dev/issue/76356).

## Invariants

- Every object in a span has size `s.elemsize == SizeClassToSize[class]` (or `npages*pageSize` for class 0), and object `n` starts at `s.base() + n*elemsize`.
- `MinSizeForMallocHeader` (512 on 64-bit) and `TinySize` (16) sit exactly on class boundaries so predicates on the user size and on the rounded size agree (`internal/runtime/gc/malloc.go:38-47`; `runtime/mbitmap.go:68-78`).
- Max waste per class is bounded by the generator's target (about 12.5% for classes above 256 bytes); the "max waste" column is `(size - prevSize - 1 + tailWaste) / spanBytes` in the worst case.
- `divMagic` is exact for every offset inside the span; the generator verifies it.

## Concurrency notes

The table is immutable. Nothing to synchronize.

## How Go does it

The table is regenerated by `go generate` from `mksizeclasses.go` (invoked via `internal/runtime/gc/sizeclasses.go` header: `//go:generate go -C ../../../runtime/_mkmalloc run mksizeclasses.go`). Go 1.26 additionally has size-specialized `mallocgc` entry points selected by size at compile time (`mallocNoScanTable`, `mallocScanTable`, `runtime/malloc.go:1080-1090`), which removes the class lookup from the hot path for constant-size allocations.

## Alternatives in other collectors

- **BDWGC**: "separate free lists for each size and kind of object", with sizes in granules (typically 16 bytes) rather than a geometric table; each heap block holds one size and kind (gcdescr.html, "Free lists per size"). Kind plays the role of Go's `noscan` bit (pointer-free, normal, uncollectable, ...).
- **Immix**: no size classes for small objects at all; objects are bump-allocated into holes of free 128-byte lines, and "medium" objects (larger than a line) get their own hole search; large objects go to a separate space. Fragmentation is handled by opportunistic evacuation, which a strictly non-moving collector cannot use.
- **jemalloc/tcmalloc-style**: Go's table is a direct descendant of tcmalloc's (`runtime/malloc.go:7-8`).

## Beskid adaptation

Beskid currently rounds requests to 8 bytes (`GcAlloc` requires `size >= 16`, 8-byte aligned, `Runtime.Mem.Gc.Allocation`) and uses bump plus first-fit free lists, with sweep-time coalescing. There are no classes.

- **Keep**: a generated class table with `divMagic`; span classes with a `noscan` bit derived from the type descriptor at allocation.
- **Simplify**: fewer classes (8-byte steps to 128, then roughly geometric with ratio 1.125 up to 32 KiB; about 45 classes), one-page spans for everything up to 1 KiB, 2-4 page spans only where tail waste would exceed 12%. Generate the table with a script checked into `compiler/scripts` so the numbers are reproducible, not hand-maintained.
- **Drop or defer**: the tiny allocator. It is an optimization for pointer-free sub-16-byte objects that complicates finalization and liveness, and Beskid's smallest object is 16 bytes with a header. Revisit only if the corelib produces many sub-16-byte pointer-free values (short strings) and profiling shows it.
- **Why**: classes are what make span bitmaps possible; without equal-sized slots there is no dense mark bitmap and no `ctz` allocation.
