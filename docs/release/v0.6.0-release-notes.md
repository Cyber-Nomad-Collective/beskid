# beskid 0.6.0 release notes

**DRAFT.** 0.6.0 is not released. The candidate is in qualification. Platform
evidence below is a placeholder until the Woodpecker runs for the frozen
candidate finish. Do not publish or quote these notes as final.

## Highlights

- One front end. The `beskid_queries` query gate is the only semantic authority
  for `check`, `build`, `run`, `test` and the language server. A program that
  `beskid check` accepts is no longer rejected by a second type checker at build
  time.
- Function values and lambdas. Functions are values: you can pass them, store
  them in fields, return them and call the result.
- A task-oriented CLI. Everyday commands sit at the root. Dependencies are added,
  removed and updated with one command each. Compiler inspection moves under
  `beskid dev`.
- Rust Glue. A Beskid library can call Rust code in process through a checked C
  ABI, with Rust owner images built from the project and admitted by digest.
- Native BSOL and serialization in Corelib, written in Beskid.
- No more toy runtime limits. Fiber, channel and other runtime tables grow on
  demand, and the managed heap has no fixed cap.

## What is new

### Language

- A function type is a reference type. Its value is a GC-managed closure record.
  Calls work through function-typed parameters, locals, fields (`holder.op(1)`)
  and call results (`Make()(1)`). A named function can be used as a value:
  `Apply(5, Double)`. A generic function is instantiated where it is read, from
  its type arguments (`Identity<i64>`) or from the expected function type
  (`i64 r = Apply(5, Identity);`).
- A lambda takes its parameter and return types from the position that declares
  the function type: an annotated local, a field, a declared return type or the
  parameter of the callee.
- Closure allocation follows use. An immutable, expression-bodied lambda that is
  only called is lowered inline and allocates nothing. A lambda in any other
  position allocates its closure record when it is evaluated.
- `for x in values { ... }` iterates an array. The array is evaluated once and
  read in index order.
- `for` also iterates any value whose type declares one zero-parameter `Next()`
  returning `Option<T>`, including generic iterators and loops inside generic
  items. The iterator is evaluated once and kept alive for the loop. Outside
  generic items, `check` rejects any other iterable with E1215.
- Every `match` that `check` accepts lowers: `when` guards (a false guard tries
  the next arm; guarded arms never count toward exhaustiveness), literal
  patterns over integer, `bool`, `char`, float and string scrutinees, nested
  generic enum payloads (`Result::Ok(Option::Some(x))`) and matches on generic
  record fields in specializations. A non-exhaustive match fails with E1304 and
  names one uncovered pattern. A bare-name guard (`when strict =>`) parses as a
  guard, not a lambda.
- A method call resolves the same way for every receiver spelling:
  `(reader).Begin()`, `(this).reader.Begin()`, contract-typed parameters and
  `where`-bounded generic parameters and fields.
- A struct literal is not admitted at the top level of an `if`, `while`, `for`
  or `match` head, so `if a == b {}` parses. Parenthesize a struct literal
  there.
- New primitive types: `i8`, `i16`, `u16`, `u64` and `f32`.
- Fields without `pub` are private to the source unit that declares the type
  (E1211).
- `Core.Output.Write(...)` and other fully qualified dependency paths resolve
  without a `use` declaration.
- Corelib modules keep their own roots: `use Core.Output;`, not
  `use Std.Core.Output;`.

### Compiler

- The legacy type checker is gone. Codegen lowers the query gate's executable
  front end through `TypedProgram`, `CodegenInput` and ISLE to Cranelift CLIF.
- A standalone `.bd` file outside a project gets the same semantic checks as a
  project file.
- `Main` is no longer reported as an unused private item.
- Faster builds from parallel item emission, streamed query snapshots,
  content-stable query reuse, a per-input line-start table for span positions,
  cached canonical paths and per-kind and per-name syntax indexes. Builder,
  dev profile, wall time (`docs/reports/2026-10-13-v06-compile-time.md`):
  Serialization Mod generation test target 180 s to about 14 s;
  `beskid check` on `compiler-sdk` 77 s to 12-15 s; Serialization Mod rebuild
  150 s to 12-14 s; runtime kit build 52 s to about 6 s.
- `beskid fmt` keeps attributes on functions, methods, fields and contract
  methods.

### Corelib

- `Core.Serialization`: format-independent data values, shape identities,
  metadata, limits and checked decimal parsing.
- `Core.Bsol`: a native BSOL lexer, parser, writer, schema validator, profile
  composition, offline import resolution, migration and typed reads and writes.
- `Core.Process`: start a child process, write to its standard input, read its
  output, wait with a deadline and terminate it.
- `Core.Json`, `Core.Dynamic`, `Core.Numeric.FloatBits`, string search,
  transform and builder helpers, number parsing and formatting, sorting and
  hashed collections, lexical paths, calendar arithmetic and `Testing.Expect`.
- Typed serialization: the compiler issues the field decoder and encoder of
  every `[Serialize]` type the program uses, generic types included.
  `Decoding.DecoderFor<T, R>` decodes from any format reader;
  `Core.Bsol.Serialization.Read<T>` and `WriteTyped<T>` read and write BSOL
  text. A `[Serialize]` application without field codec facts (`Pair<Opaque>`)
  fails the build and names the field.
- Registered Dynamic mapping (DYN-06-03/04): `Dynamic.Mapping<S, D>()` returns
  a token only for a lossless plan (fields by name, lossless integer widening,
  `None` for an absent optional destination). `Dynamic.Map` builds a fresh
  destination; narrowing, sign change, string coercion, unknown or missing
  fields reject the whole mapping with no partial result.
- String and hash performance. Builder, debug runtime kit, 1e5 iterations, per
  operation: `==` against a literal 5-6.6 us to 1-2 ns; `CompareOrdinal` 513
  to 50 ns; `StringMap` lookup 1527 to 95 ns; `I64Map` lookup 1022 to 55 ns;
  interpolation 19.7 to 2.6 us; concatenation 14.8 to 1.2 us. `String.Join`,
  `Repeat` and `Replace` are linear (Join of 16k lines: over 10 minutes to
  about 4 ms). `String.Trim` also trims LF and CR.

### Runtime

- Runtime tables for fibers, channels, mutexes, wait groups, hubs, poll tasks
  and external waits grow on demand. Records never move, so handles stay valid.
- `BESKID_HEAP_MAX` caps the managed heap (decimal bytes, optional `k`, `m` or
  `g` suffix). Without it, the heap has no fixed cap.
- `BESKID_FIBER_STACK_MAX` sets the per-fiber stack reservation. The default is
  8 MiB; the value must be a whole multiple of 64 KiB.
- On Windows, a network transfer that completes as its deadline fires keeps its
  data instead of losing it. A cancelled operation waits at most 250 ms for its
  completion. If the completion comes later, the call still returns at once, that
  direction reports `Busy` until the completion arrives, and a stream that moved
  bytes in that late completion fails with `ConnectionAborted`.

### Mods

- Native Mods are compiled ahead of time and run in the native Mod host. Their
  descriptor (`mod.descriptor.json`, schema 3) records each build tool by
  digest and version output.
- Generators contribute typed syntax, not source strings.
- The toolchain ships the Corelib Mods prebuilt. Your own Mods are built by
  `beskid dev mod rebuild` or by any `build`, `run` or `check` of the project
  that uses them.

### Interop (Rust Glue)

A project declares a Rust owner in its manifest:

```bsol
glue "glue_manual" {
    backend = rust
    path = "rust"
}
```

The label is the native library identity. It matches the `Library` string of
the `Extern` contracts and `[GlueHandle]` types that the owner implements.
`[RustOwner(Path: ..)]` maps a method or handle type to a Rust path under the
generated `implementation` module.

Build the consumer with explicit tools:

```bash
beskid build --backend glue-rust --linker <path> --rust-toolchain <prefix>
```

`--cargo` together with `--rustc` can replace `--rust-toolchain`. The build
produces a shared Glue consumer and one Rust owner image per `glue` block. Each
image carries an admission record, and the consumer record pins each owner image
by digest.

Admitted boundary types: fixed-width integers, `f32` and `f64`, `bool`,
Unicode scalars, UTF-8 and byte views, arrays, unit and branded opaque handles.

### CLI and tooling

```text
beskid new <name> [--template <template>] [--list]
beskid check | build | run | test | fmt | doc
beskid add <package>[@<version>] [--path <dir>] [--project <manifest>]
beskid remove <package>
beskid update <package> [--version <version>] | --all [--dry-run]
beskid package search | info | pack | publish | login | logout | template
beskid toolchain status | update
beskid doctor
beskid dev <inspection or maintenance command>
```

- `add`, `remove` and `update` change the manifest and `Project.lock` together.
  A failed resolution leaves both files unchanged.
- Registry dependencies resolve and lock transitively. `remove` drops
  transitive packages nothing else reaches; differing requests for one package
  fail and name both requesters. Change records list transitive pins that
  changed.
- `--locked`, `--offline` and `--frozen` work on `check`, `build`, `run`,
  `test`, `add`, `remove` and `update`.
- `beskid new` works offline with the bundled application template.
- LSP: the `modHost` initialization option selects the Mod host and runtime
  kit. Project preparation failures appear as a `project-preparation`
  diagnostic.

## Breaking changes

Beskid has no users yet. These are listed for the record; there is no migration
path.

| Change | Effect |
|---|---|
| Root commands moved | `analyze` is `check`, `format` is `fmt`, `pckg` is `package`, `up` is `toolchain`. `parse`, `tree`, `clif`, `fetch`, `lock`, `graph`, `mod`, `import`, `lsp`, `runtime-kit`, `corelib`, `repl`, `validate-bsol` and `migrate-bsol` live under `beskid dev`. The old spelling fails and names the new one. |
| `Std` namespace removed | `Std.`-qualified paths fail with E1105 or E1108. The Corelib dependency label is `Core`. |
| Default field privacy | A non-`pub` field read or built outside its source unit fails with E1211. |
| Struct literals in heads | A struct literal at the top level of an `if`, `while`, `for` or `match` head must be parenthesized. |
| Module path ambiguity | A logical module path that two packages provide fails with E1104. |
| Capturing `mut` locals | A lambda that captures a `mut` local or a native pointer outside `spawn` fails with E1233. |
| Heap cap variable | `BESKID_HEAP_MAX_BYTES` is replaced by `BESKID_HEAP_MAX`. |
| Pipeline phase ids | `lower.ast`, `lower.resolve_pass1`, `lower.normalize`, `lower.resolve`, `lower.type_check` and `semantic.error_handling` are no longer emitted. |
| OS threads | `Thread.Spawn`, `Thread.Join`, `Thread` and `ThreadError` are removed. Use fibers. `Thread.Yield` remains. |
| 0.4 Glue scaffold | The seven Glue Mod contracts, `[Glue]`, `[GlueImport]`, `[GlueExport]` and `GlueBackendKind` are removed. |

## Known limitations and deferrals

- **Glue extensions move to 0.6.1** (`v061-glue-extensions`): records by value,
  callbacks and function types, Glue-driven exports (the Rust side of an export
  is linked by hand today), enums, and one boundary vocabulary shared with
  Interop.Contracts.
- **Glue stdio bridge is provisional.** `Core.Glue` (envelope, binary codec,
  pump, session) has no 0.6 obligation. Its 15 release cases fail closed and are
  not evaluated.
- **`glue-dotnet` is unavailable.**
- **Isolate parallelism is planned for 0.6.1 to 0.6.5**: attributes and isolate
  prerequisites (0.6.1), captures, `move` and incremental marking (0.6.2),
  isolates and scopes (0.6.3), ports and pipelines (0.6.4), parallel sequences
  with ORCA-style sharing (0.6.5). 0.6.0 has fibers only.
