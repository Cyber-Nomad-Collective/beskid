A diagnostic has four parts: the code, the message, the span, and sometimes a hint. Read the span first. The message is usually right about what is wrong and often wrong about where you should be looking, because the real cause is a `pub use` two modules away.

```text
error[E1101]: unknown value `invioce`
   ┌─ Src/Billing.bd:14:12
   │
14 │     return invioce.totalCents;
   │            ^^^^^^^ not found in this scope
   │
   = help: a local named `invoice` is in scope
```

The CLI and the language server print the same report from the same analysis, so a diagnostic that appears in the editor and not in `beskid analyze` means the two are running different versions or looking at different project roots. Fix that before you fix the code.

## The code bands

Codes are stable. Search for one in the standard's [diagnostic registry](/platform-spec/compiler/semantic-pipeline/diagnostic-code-registry/) and you get the rule that produced it. The bands you will meet first:

| Band | Area | Examples |
| --- | --- | --- |
| E11xx | names and imports | E1101 unknown value, E1104 ambiguous import, E1105 unknown import path, E1107 private item, E1109 missing import |
| E12xx | types | E1201 unknown type, E1204 wrong number of arguments, E1206 type mismatch, E1208 non-bool condition, E1214 assignment to immutable |
| E13xx | enums and match | E1301 unknown variant, E1305 arm type mismatch |
| E16xx | contracts | E1601 missing required member, E1607 invalid conformance target |
| E18xx | manifests and mods | E1894 legacy `Project.proj` |
| W11xx | warnings | W1103 shadowed local, W1110 ambiguous missing import |

Errors stop the build. Warnings do not, and the correct number of warnings in a repository is zero, because a warning you have learned to ignore is a warning you will not see when it matters.

## The three you will hit on day one

**E1105, unknown import path.** `use Std.Core.Optinal;` with a typo, or a module that exists but is not reachable from this target. The compiler now rejects these outright instead of letting the program proceed with a missing module and failing later on E1101 for every symbol it would have provided. Check the spelling, then check chapter 04 for whether the file is where the module path says it is.

**E1204, wrong number of arguments.** Either you called a function with the wrong arity, or you called a generic with the wrong number of type arguments. The message tells you which and shows the signature it expected.

**E1214, cannot assign to immutable binding.** Add `mut`. Or do not, and restructure so the value is computed once. Both are fine; the compiler is only insisting that you choose.

## Legality is scoped to what you build

The semantic gate checks the items a target reaches, not every file under `root`. A broken helper in a module nothing imports does not stop `beskid build --target App`. This is intentional and it cuts both ways: a fast build on a large repository, and a test target that can be red while the application target is green. Run `beskid analyze` per target, and run the test target in CI, or you will ship the green one and find out about the red one from a customer.

## When the message feels wrong

It usually is not. But the span can be far from the cause. The common shapes:

- E1101 on a name that clearly exists: the defining module is not `pub`, or the `use` line is missing, or the file's `mod` declaration does not match its path.
- E1206 type mismatch on a call that looks right: a `pub use` re-exported an older type with the same name, and the two `Invoice` types are different nominal types.
- E1201 unknown type in a file you did not touch: a manifest change moved `root`, and a module path stopped resolving.

Minimize first. Copy the failing function into a single file, run `beskid analyze` on it, and confirm the diagnostic still appears. If it disappears, the cause is in the project graph, and `beskid graph --kind imports` shows you the graph.
