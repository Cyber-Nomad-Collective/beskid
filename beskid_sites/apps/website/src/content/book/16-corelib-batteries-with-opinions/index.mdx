The standard library is not `System.*`, a forty-year accretion where `System.IO.File` and `System.IO.Abstractions` and `Microsoft.Extensions.FileProviders` all exist because nobody could delete the previous one. It is a workspace of eleven Beskid packages, written in Beskid, with a dependency graph you can print.

```text
corelib/
├── CoreLib.bws                   the workspace
├── beskid_corelib/               package "corelib": the aggregate everyone depends on
└── packages/
    ├── foundation/               Core.*: Results, Optional, Collections, String, Bytes,
    │                             IO, FS, Time, Args, Disposable, Error, Output
    ├── runtime/                  process init, host linkage
    ├── concurrency/              Fiber, Channel, Mutex, WaitGroup, Hub
    ├── console/                  ANSI, formatting, terminal capabilities
    ├── network/                  Dns, Tcp, Udp
    ├── http/                     HTTP/1.1 client and server
    ├── interop/                  FFI profiles
    ├── glue/                     cross-language glue (0.6 target)
    ├── compiler-sdk/             Beskid.Compiler.*, Beskid.Syntax for mods
    └── pest-gen-schema/          grammar generation support
```

Three things follow from that layout. The resolver injects `corelib` into every project, so you never declare it and `Core.*` is reachable without an import. `beskid doc` generates the API reference from the same `///` comments the language server shows on hover, so there is one documentation source and it cannot drift from the signatures. And when something in `Core.IO.ReadExact` surprises you, you open `Core/IO/IO.bd` and read thirty lines of Beskid, because that is what it is.

The chapter covers the `corelib` command for getting that tree on disk, how injection and discovery work, the I/O, networking, and HTTP packages that arrived together, the console package, the documentation pipeline, and which surfaces are thin wrappers over runtime builtins versus pure Beskid.
