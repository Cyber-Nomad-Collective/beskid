Threads are expensive. `async`/`await` is threads with extra syntax, two colors of function, and a decade of conference talks explaining why your `ConfigureAwait(false)` was in the wrong place. Beskid has `spawn`, which gives you a cooperative fiber and a typed handle, and channels, which are how fibers talk. That is the whole surface.

```beskid
use Std.Concurrency.Fiber;
use Std.Concurrency.Channel;
use Std.Core.Output;

i64 Sum(Channel<i64> input) {
    mut i64 total = 0_i64;
    mut bool open = true;
    while open {
        match Channel<i64>.Receive(input) {
            Result::Ok(n) => { total += n; },
            Result::Error(_) => { open = false; },
        };
    }
    return total;
}

unit Main() {
    Channel<i64> numbers = Channel<i64>.Create();
    Fiber<i64> summer = spawn Sum(numbers);

    for n in range(1, 11) {
        Channel<i64>.Send(numbers, n);
    }
    Channel<i64>.Close(numbers);

    match summer.Join() {
        Result::Ok(total) => Output.WriteLine("sum = ${total}"),
        Result::Error(_) => Output.WriteLine("worker failed"),
    };
}
```

`spawn Sum(numbers)` starts `Sum` on its own fiber and hands back a `Fiber<i64>`, typed by what `Sum` returns. The parent feeds a channel, closes it, and `Join` waits for the result. No thread pool, no synchronization context, no `Task.Run` versus `Task.Factory.StartNew` trivia question.

The chapter covers the evaluation model and why there is no `async`, then `spawn` and the handle's three operations, then channels and the other primitives, then where all of it lives in the corelib and the runtime. `async` and `await` are reserved words and compile errors, so the porting strategy of `#define await` will not save anyone.
