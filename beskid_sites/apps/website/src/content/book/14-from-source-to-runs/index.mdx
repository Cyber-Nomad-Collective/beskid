Compilation is a pipeline, not a séance. Every stage has a crate, a command that exposes it, and a diagnostic band it is allowed to emit. This chapter walks the reference compiler from a manifest to a native binary.

```text
manifest ──► resolution ──► parse ──► semantic facts ──► lowering ──► CLIF ──► object ──► link
 .bproj      beskid_analysis   beskid_analysis   beskid_queries    beskid_isle   Cranelift  beskid_aot   beskid_aot
             (projects)        (syntax, parser)  (Salsa)           beskid_codegen
```

Three things to know before the detail. The output is native code; there is no bytecode and no interpreter in the shipped path, and `beskid run` builds a binary and executes it. Semantic facts are computed once in a Salsa database and shared by the CLI, the language server, and the lowering, so the editor and the build cannot disagree about what a name means. And lowering goes through ISLE, the same term-rewriting language Cranelift uses for its own backends, which is how runtime pieces are being moved from Rust into Beskid one rule at a time.

The pages that follow: the pipeline as a whole, the front-end, the semantic pipeline and where diagnostics come from, lowering and IR, the two places JIT still exists, the AOT build and link, and the `clif` command for when you need to see what the compiler actually emitted. The stage contracts are normative under [build pipeline](/platform-spec/compiler/build-pipeline/).
