## Context

Historically the compiler seeded compilation from every effective root **`Prelude.bd`**, unioning `pub mod` lines across the aggregate corelib and workspace shards. That implicit surface made Tier-1 vs Tier-2 boundaries opaque, complicated aggregate vs shard layouts, and diverged from normal dependency + `use` semantics. The **`.bproj` / `.bws`** manifest migration aligns project metadata with Bsol and removes legacy `Project.proj` / `Workspace.proj`.

## Decision

| Rule | Detail |
| --- | --- |
| Prelude retirement | Tooling **must not** automatically inject or seed modules from **`Prelude.bd`** (no `include_std_prelude` / prelude union in program assembly) |
| Visibility | Reachable symbols come from **manifest dependencies** plus **explicit `use`** imports on the entry module and its transitive `use` graph |
| Graph attachment | Host projects **still** receive implicit **corelib aggregate** path wiring in `resolve_dependencies` — unchanged from [Corelib injection and resolution](/platform-spec/core-library/compiler-integration/corelib-injection-and-resolution/) |
| Aggregate corelib | Canonical **`corelib.bproj`** uses **`type = Aggregate`**; it **must not** ship **`Prelude.bd`**; shard packages expose modules under their own source roots |
| Superseded ADRs | **D-COMP-BUILD-0022**, **D-CORE-COMP-0009**, and **D-CORE-API-SHAPE-0002** are **Superseded** by this decision |

Authors who previously relied on prelude re-exports **must** add explicit `use` paths (for example `use Console.Ansi;`) and declare path or registry dependencies where needed.

## Consequences

- Assembly discovers modules via **import closure** or **workspace scan** only—never via prelude `pub mod` harvesting.
- Corelib CI no longer maintains prelude tier guards tied to `Prelude.bd` membership; tier policy applies to published modules and explicit imports.
- Template and scaffold output **must not** assume prelude-visible builtins; starter sources include explicit `use` for corelib modules they reference.
