## What this article covers
This article explains the `design-model` view for `Project manifest contract` in concrete, onboarding-first language.

## Package readme (`readme`)

The `project` block **may** include `readme = "relative/path.md"` (quoted POSIX-style path relative to the project root). When omitted, tooling treats **`readme.md`** at the project root as the default readme when that file exists. `beskid pckg pack` publishes the resolved file for registry documentation (typically as root **`README.md`** in the `.bpk` artifact). The same optional field is available on the `workspace` block in **`Workspace.proj`**.

## Mod project type (`Mod`)

`Project.proj` carries a **project kind** / **type** field on the `project` block. When set to **`Mod`**, the manifest denotes a compiler-mod package. The compiler discovers these packages through dependency resolution, compiles them AOT, caches artifacts in the package/object cache, and loads their contracts during host compilation.

User-visible semantics of Beskid-side contracts remain in **[Compiler Mod SDK](/platform-spec/language-meta/metaprogramming/compiler-mod-sdk/)**; this contract defines manifest shape and validation so resolution, lockfiles, and the Rust mod host agree on inputs.

### On-disk nesting under `project`

In `Project.proj`, mod configuration lives in a nested block under `project`:

```text
project:
  name: ...
  type: Mod
  mod:
    maxGeneratorRounds: 4
    capabilities: [emit_syntax]
```

Hosts must parse this as part of the `project` aggregate, not as a free-floating top-level block kind. Unknown keys inside `mod` must error unless explicitly reserved.

### Validation phases

1. **Structural parse** — While building `ProjectManifest`, reject duplicate keys, illegal types, and unknown `mod` keys.
2. **Graph validation** — While building workspace/project DAGs, detect invalid compiler-mod dependency topology and incompatible capability/dependency requirements.

Each phase must use distinct stable diagnostic codes from the **E1801–E1899** mod/manifest band documented in **[Diagnostic code registry](/platform-spec/compiler/semantic-pipeline/diagnostic-code-registry/)**.

### Normative `project.mod` shape (v0.2 target)

Hosts must validate the following keys when `type: Mod`. Unknown keys are rejected with stable diagnostics unless explicitly reserved.

| Key | Required | Meaning |
| --- | --- | --- |
| `maxGeneratorRounds` | no | Positive integer cap on generator replay loops per host compilation generation; default `4` when omitted. |
| `capabilities` | no | Closed vocabulary list granting compile-time powers (`emit_syntax`, `read_project_sources`, `query_semantic_snapshot`, `extern_ffi`, `rewrite_syntax`). |
| `artifactPolicy` | no | Artifact-cache policy for fetched mods (`reuse`, `rebuild`, `clean_rebuild`); workspace mods use eager hash-based incremental checks. |

Discovery is contract-based and does not require `attachTo`/`entryModules`; scope narrowing belongs to `Collector` implementations.

### Non-`Mod` projects and compiler-mod contracts

Default platform policy: compiler-mod contracts are valid only in `type: Mod` projects. Host projects (`App`/`Lib`/`Test`) consume mod artifacts through dependencies, not by defining contracts inline.

`Mod` projects are the supported carrier for compiler mods.

## Code anchors
- Manifest loading and CLI-style `resolve_input` in `compiler/crates/beskid_analysis/src/services.rs`
- Workspace-aware `Project.proj` discovery in `compiler/crates/beskid_analysis/src/projects/manifest_resolve.rs`
- `CompilationContext` for analysis and LSP in `compiler/crates/beskid_analysis/src/compilation_context.rs`
- Project graph and `CompilePlan` in `compiler/crates/beskid_analysis/src/projects/compile_plan.rs` and `compiler/crates/beskid_analysis/src/projects/graph/`
- CLI project graph setup in `compiler/crates/beskid_cli/src/commands/`

## Practical guidance
When changing behavior in this area, update both the contract text and the corresponding compiler/runtime or tooling tests in the same change so the specification remains executable.
