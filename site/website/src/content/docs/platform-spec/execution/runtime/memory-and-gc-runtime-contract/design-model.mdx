## What this article covers
This article explains the `design-model` view for `Memory and GC runtime contract` in concrete, onboarding-first language.

## Newcomer walk-through
Start from the parent feature hub to learn the contract boundaries, then map the behavior to the listed implementation anchors before reading test coverage.

## Code anchors
- Runtime memory exports in `compiler/crates/beskid_runtime/src/lib.rs`
- Abfall heap/runtime integration in `compiler/crates/abfall/src/heap.rs` (`allocate_beskid`, external roots, write barrier)
- ABI contracts in `compiler/crates/beskid_abi/src/lib.rs`
- JIT linking and call setup in `compiler/crates/beskid_engine/src/jit_module.rs`

## Fiber phases (GC interaction)

| Phase | Normative behavior |
| --- | --- |
| **A (first ship)** | Many fibers, **one GC mutator** over an active runtime heap session; `gc_write_barrier` is an abfall-backed insertion barrier for descriptor-traced payload pointers |
| **B (documented)** | Parallel mutators + real insertion barriers on pointer stores; see `/execution/memory/gc.md` |

Scheduler and stack contracts: **[Fiber scheduler and stacks](/platform-spec/execution/runtime/fiber-scheduler-and-stacks/)**.

## Runtime surface

The runtime memory surface is split between allocation/rooting builtins and diagnostic builtins:

| Builtin family | Contract |
| --- | --- |
| `alloc`, `gc_register_root`, `gc_unregister_root`, `gc_root_handle`, `gc_unroot_handle`, `gc_write_barrier` | Allocate descriptor-backed payloads, manage embedder root slots and temporary handles, and shade newly stored child pointers during marking. |
| `gc_bytes_allocated`, `gc_object_count`, `gc_phase`, `gc_collect`, `gc_collect_if_needed`, `gc_external_root_count` | Expose heap state and collection controls for generated code, tests, and host diagnostics. These are always available runtime exports, not metrics-feature counters. |

Host tooling uses `beskid_runtime::runtime::GcSnapshot` as the Rust snapshot wrapper around the active `abfall::Heap`. CLI, engine, and test code should read heap state through that module instead of reaching into heap internals.

## Practical guidance
When changing behavior in this area, update both the contract text and the corresponding compiler/runtime or tooling tests in the same change so the specification remains executable.
The runtime no longer relies on arena-wide permanent roots; allocations flow through `abfall::Heap::allocate_beskid` and are reclaimed by mark/sweep once they become unreachable from registered roots.
