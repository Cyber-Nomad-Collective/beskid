## Context

0.6.3 is the first release that runs user code on a second core. It depends on 0.6.1 (`thread_create`/`thread_join` and atomic intrinsics, the process-wide worker pool, the `ProcessInit`/`IsolateCreate` split, the region-to-owner map, the normative non-moving collector rule, the foreign-reference definition, `TYPE_DESCRIPTOR_IMMUTABLE`, the `transfer_class` query and marker contracts) and 0.6.2 (`[Captures(Bound: C)]`, `move`, the alias discipline). Names, diagnostic codes and terms follow the shared vocabulary of `openspec/changes/v061-attributes-and-isolate-prerequisites/design.md`, including the names this change introduces (listed there under "Names introduced by 0.6.2-0.6.5"); the archive order and the delta chains this change takes part in are in the same design. Everything here is runtime (Beskid corpus and C host) and corelib work, plus the static E1249 rule; the method type parameters and inference that the fluent `s.Spawn(() => ...)` form needs are 0.6.1 prerequisites.

Locked inputs: rulings 1-13 of the isolate design decision and D1-D14 of the Pony-derived decision (`docs/reports/2026-10-04-v06-decisions.md`, entries of 2026-10-13). This document specifies them; it does not reopen them.

## Decisions

### Isolate entry runs in a fiber
`FiberPanic` traps when there is no current fiber. Running the isolate entry as the first fiber of the isolate's scheduler reuses the whole fiber outcome machinery (`FIBER_JOIN_PANICKED`, owned message at offset 56) without a second panic path. The join protocol reads the message through the child heap before the heap is discarded, allocates a copy in the joiner's heap, then releases the child. This is the same copy-out the 0.6.1 proposal promised for the main fiber.

### Serial elision instead of blocking on the pool
Ruling 10 lets a task open a nested scope on the shared pool. A bounded pool plus blocking spawn deadlocks when every pool isolate waits for a slot its own child needs. Running the body inline when `__isolate_spawn` returns `-1` is deadlock-free, preserves semantics (captures are the same values; `Shared` by pointer is trivially a pointer in the same heap; `Copied` need not be copied) and gives ruling 12's "one core is serial and deterministic" for free. Cilk's work-first principle (Frigo, Leiserson, Randall, PLDI 1998, https://doi.org/10.1145/277650.277725) is the precedent: the serial elision of a fork-join program is a valid execution.

### Structured failure
Ruling 8: a failed task cancels its siblings and the scope reports every failure in spawn order. The spec makes the report independent of timing by sorting failures by spawn index and by counting every failed task, joined or not. This is X10's rooted exception model (Charles et al., OOPSLA 2005, https://doi.org/10.1145/1103845.1094852) with Featherweight X10's finish semantics (Lee and Palsberg, PPoPP 2010, https://doi.org/10.1145/1693453.1693459); the cancellation-flows-down rule follows Kotlin structured concurrency, Swift task groups and Trio nurseries, which the SOTA document records as the practitioner consensus. Tolerated failures are ordinary `Result` values, which keeps the "failed task" notion crisp: a panic or a `SpawnTry` `Error`.

### Scoped sharing before counts
Ruling 6 (amended): 0.6.3 passes `Shared` scope captures by pointer rooted by the scope frame. Pony doc 2.4.3 shows this is a sound ORCA specialisation: a count of one held by the frame, released at join, with no messages because structure bounds the lifetime. The child's recording of foreign references during marking is the FRC table of ORCA (Clebsch et al., OOPSLA 2017, https://doi.org/10.1145/3133896, sec. 4), built in 0.6.3 so that 0.6.4 adds counts to an existing table.

### Heap adoption at join (D7)
D7: adopt the joined task's heap regions into the parent when the count-table merge is a rename. In 0.6.3 no isolate but the parent can hold a pointer into a child heap (ports do not exist; a grandchild's foreign entries name the grandparent's objects, not the child's), so the merge is always a rename and adoption is unconditional for completed tasks. The non-moving collector means no pointer is rewritten; ORCA relies on the same property, and MaPLe's hierarchical heaps adopt child heaps at join in the same way (Raghunathan et al., ICFP 2016, https://doi.org/10.1145/2951913.2951935; Westrick et al., POPL 2020, https://doi.org/10.1145/3371115). The fallback (a child whose local table names a third isolate: retention, then adoption at scope exit) is specified in 0.6.4 and completed in 0.6.5. Failed and cancelled heaps are discarded whole, Erlang-style fault containment (Armstrong, HOPL III 2007, https://doi.org/10.1145/1238844.1238850).

### Transit as an Erlang-style structural copy
Option 2 of compiler-requirements 3.5: descriptor-driven deep copy (Erlang `copy_struct`; Johansson, Sagonas, Wilhelmsson, ISMM 2002, https://doi.org/10.1145/773039.512440, measure private-heap copying and find small messages dominate; Carlsson, Sagonas, Wilhelmsson, TOPLAS 2006, https://doi.org/10.1145/1146813, show escape analysis can elide copies later). The copier runs on the destination mutator while the source is quiescent, which preserves Phase A per heap. The refusal list is the validation `ManagedObjectForReference` already performs, applied fail-closed.

### ReadOnlyArray.Freeze (D5, ruling 7)
`Freeze(move T[])` is Pony's `consume val x` and Gordon et al.'s isolated-to-immutable conversion (OOPSLA 2012, https://doi.org/10.1145/2384616.2384619): uniqueness at the moment of freezing makes the result safe to share. `ReadOnlyArray<T>` is `[Immutable]` with its one array field marked `[ImmutableStorage]` (the 0.6.1 corelib-only exemption), Shared when `T` is Shared.

## Open issues

Closed on 2026-10-13 by the 0.6.1 prerequisites and vocabulary: the host processor count (former issue 1) is the 0.6.1 `host_processor_count` intrinsic; generic result inference and the method form (former issue 2) are the 0.6.1 requirements "Generic methods and method type arguments" and "Method type argument inference", so the spec uses `s.Spawn(() => ...)`; the vocabulary re-check (former issue 5) is done and needs no new diagnostic code; the per-field capture classification (former issue 4) is answered by the 0.6.1 descriptor flag `TYPE_DESCRIPTOR_IMMUTABLE`, which the requirement "Isolate spawn and join builtins" reads, so neither a corelib table nor a compiler-emitted class map is needed.

1. Where exactly the scope frame's root handles are released when the body exits by panic in the parent (the parent's own main fiber panics while tasks run). The spec requires the scope to join every task on every exit path; a panic in the body is a parent-isolate panic (process-fatal in the main isolate, task failure in a nested one), and the runtime must still cancel and join the children before the isolate ends. The implementation hook is the isolate shutdown path, not the corelib.

## Implementation rulings (2026-10-15, v06x parallel program)

Sources: `~/.claude/handoffs/v06x-rt-progress.md` (D11-D17), `v06x-par-progress.md` (D1-D9), `v06x-lang-progress.md`.

- Builtin names (rt D11). The runtime adopts the corelib names exactly: `__isolate_spawn<T>`, `__isolate_spawn_local<T>`, `__isolate_wait`, `__isolate_join`, `__isolate_join_value<T>`, `__isolate_join_message`, `__isolate_join_finish`, `__isolate_current`, `__isolate_main`, `__isolate_task_status`, `__isolate_task_index`, `__isolate_task_isolate`, `__isolate_cancel`, `__isolate_cancel_requested`, `__isolate_scope_open`, `__isolate_scope_cancel`, `__isolate_scope_close_ports`, `__isolate_scope_close`, `__isolate_scope_port`, `__isolate_pool_size`, `__isolate_idle_count`. The join result is split into status and typed value (`__isolate_join` and `__isolate_join_value<T>`), as fibers split status and value, because a builtin cannot return both. `__isolate_task_status` answers 4 while running and 3 for an unknown handle.
- Thread entry (rt D12). A C trampoline starts the isolate thread through the intrinsic `isolate_thread_start`, which calls the Beskid export `beskid_rt_v5_isolate_task_run`.
- Registry lock (rt D13). One process-wide spin lock guards scopes, tasks, the port table and isolate ids; lock order is parallel lock, then port ring mutex, then transport lock. Handles and ids are serials that are never reused; `BESKID_ISOLATES_MAX` is bounded at process start.
- Transit (rt D14). One native record format serves spawn captures and `Copied` port messages: the capture walk runs on the source thread with fail-closed refusals ("transit refused 0x<descriptor>"), materialization on the destination thread in three passes. Spawn captures of `Shared` objects pass by pointer under a scope root held until the join.
- Adoption (rt D15). A completed task is always adopted; the parent completes any cycle in progress first so adopted spans need only the parent's sweep generation.
- Cross-isolate waits (rt D16) reuse the owner mailbox; outside a fiber the waiter drives the scheduler. The mailbox grows instead of trapping at 256 entries.
- Cancellation (rt D17). A per-instance watch list holds the cancel word, fiber handle and task; the scheduler applies cancel requests before pending cancels and a store sets the word and posts a wake-up.
- Scope exit (par D5). The scope cancels when the body returned `Cancelled`, closes its ports, joins every task in spawn order, and reports failures in spawn order (including tasks joined earlier); `Failed` beats `Cancelled` beats the body result. `workers: 0` means the process bound.
- Elision (par D3, D4). Serial elision runs the body as a runtime-registered local task (a fiber), so panics stay task failures and keep their spawn index. `s.Isolate` at the bound runs the body as a concurrent fiber of the caller, because a blocking inline body would deadlock the inbox pattern.
- `SpawnTry` (par D6) is `Spawn` of a body that panics with the error message. A failing task cancels its siblings and completes the waits parked on its scope's ports with status 2.
- Module layout (par D1, D2). `Core.Parallel` lives in the package `corelib_concurrency`; the types are in `Core.Parallel.Scopes`, `Isolate`, `Port` and `ReadOnlyArray` because the function `Scope` and the type `Scope` cannot share one module path. Spec scenarios that write `use Core.Parallel;` and use `Scope` bare read as the matching `use` of the submodule.
- Equality (lang R-lang-8). There is no structural `==` in 0.6.x; handle comparison is written `Equals`, and spec examples that write `Isolate.Current() != parent` read as `!Isolate.Current().Equals(parent)`.
- Busy-loop cancellation (par S-2). The `TwoFail` scenario expects both failures only if the busy loop of the slow sibling has no cancellation safepoint; the runtime does not promise it, and tests that need both failures keep the slow sibling free of cancellation safepoints.
- `[NeverTransferable]` on `Fiber`, `Channel`, `Hub`, `Mutex`, `MutexGuard`, `WaitGroup` and the socket handles is applied in the corelib (lang).
